## Description
The five legacy anomaly rules (large amount, foreign currency, odd hours, card testing, duplicate charge) existed, but nothing ever ran them. They now run on every new transaction the pipeline stores. Each finding is recorded as an anomaly, and the user is alerted when it is worth it.

## Acceptance criteria
- [x] **The hook:** the pipeline tells listeners about every stored transaction, after the commit (a `TransactionCreatedListener`, Observer pattern).
  - A failing listener is logged and never fails the event or the other listeners.
  - A re-processed event passes the transaction stored the first time, never a phantom copy.
- [x] **What is checked:** spends only. Refunds, income and transfers are never checked.
- [x] **Context is taken relative to the transaction's own time,** not today. This fixes the legacy bug that judged imported statements against the wrong window.
  - **Average:** the user's spends in the same category during the 30 days before the transaction.
  - **Duplicates:** the same amount at the same merchant in the 24 hours up to it, including the same minute. The transaction itself never counts.
  - **Odd hours:** judged in the user's time zone. A missing or invalid zone falls back to India time.
- [x] **Large amount:** only from ₹2,000, and only with at least 3 earlier spends in the category, so a first-ever purchase isn't "3x the average".
- [x] **At most one anomaly per transaction:** the service checks first, and the V20 unique index refuses a racing second save. It is idempotent across re-claims and API instances.
- [x] **Alerts:** an anomaly is always recorded (it shows under Anomalies). A critical **ANOMALY** notification (it ignores quiet hours, D-51) is sent only when:
  - its confidence is ≥ 0.7 (a lone 1 a.m. food order, at 0.6, is recorded quietly);
  - the transaction is from the last 3 days, so importing old statements doesn't flood the phone.
- [x] **The alert itself:** "Unusual charge: ₹1.00 at STRIPE*TEST", with the rules' reasons as the body. A tap opens `/anomalies/{id}` (the Web Push URL comes from AOS-510).

## Design
- **Context:**
  - The pipeline (D-34) already turns every source into transactions.
  - Notifications are delivered by D-51.
  - Bill matching (AOS-508) needs the same "after a transaction is stored" moment.
- **Options considered:**
  1. **Observer hook in `IngestProcessor`, after the commit** (chosen). It is one place for every source, the reactions stay out of the pipeline's transaction, and a new reaction is one class.
  2. **A pipeline step.** It would run inside the write transaction, so a slow detector or a notification failure would hold or roll back the transaction.
  3. **A scheduled sweep.** Alerts would arrive minutes late, and it needs a "checked" marker.
- **Decision:** option 1 (D-53). **Patterns:**
  - Observer (`TransactionCreatedListener`);
  - Specification/rule objects (the existing `AnomalyRule`s);
  - idempotency by a unique constraint.
- **Extensibility:**
  - a new rule is one `AnomalyRule` in the detector's list;
  - a new reaction (AOS-508 bill matching) is one listener registered in Koin.
- **Impact:**
  - **Changed:**
    - `IngestOutcomeWriter.processed` now returns the stored transaction;
    - `IngestProcessor` takes `listeners`;
    - `AnomalyDetectorService.evaluate(Transaction)` (new signature, now also uses `UserRepository`);
    - `LargeAmountRule` gains a minimum;
    - `DuplicateChargeRule` excludes itself by id;
    - `AnomalyRepository.findByTransactionId`.
  - **New:** `AnomalyAlerts`, and V20, a unique index on `anomalies.transaction_id`.

## Verification
- **Overall:** `./gradlew test integrationTest koverVerify` passes with 1,162 unit and 102 integration tests, none disabled, and 99.4% line coverage.
- **Detector (fixed time, no dependence on the real clock):**
  - the average window (outside the window, later, and other-category spends don't count);
  - the ₹2,000 minimum and the 3-spend minimum;
  - imported rows judged against their own past;
  - duplicates, including the same minute and excluding 25 h earlier;
  - user zones, including an invalid one;
  - combining several rules;
  - one anomaly per transaction, including a racing save.
- **Alerts:**
  - a confident and recent anomaly alerts, with its title, body and link;
  - a missing merchant still reads well;
  - low confidence or an old transaction is recorded only;
  - a second look sends nothing more.
- **Hook:**
  - all listeners hear about each stored transaction;
  - a failing listener is isolated;
  - a re-processed event passes the stored transaction;
  - ignored events reach no listener.
- **Postgres end to end:** a ₹1 "STRIPE*VERIFY" SMS becomes a transaction, a CARD_TESTING anomaly and one in-app alert. Re-checking adds nothing, and V20 refuses a duplicate.

## Risks / notes
- **Delivery isn't guaranteed:** if the process dies after the commit but before the listener runs, that transaction is not checked unless the event is re-claimed. A sweep for unchecked recent spends can close this later if it matters.
- **Duplicate overlap:** a pair the dedup step was unsure about (in Review, AOS-309) can also raise a "duplicate charge" anomaly. That is acceptable: both point to the same question.
- **Unused methods:** `TransactionRepository.getCategoryAverage` and `getRecentByMerchant` (which measure from "now") are no longer used by the detector. They're kept until a cleanup task.
- **AI explanation:** the Go worker's Claude explanation (`anomaly_explain`) is still not queued; it depends on the queue payload fix (AOS-506/509).
