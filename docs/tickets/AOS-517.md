## Description
`SubscriptionDetectorService.detectSubscriptions` re-saved every merchant group with a regular pattern in the 400-day window as `ACTIVE`, whatever its last charge date. `endStopped` then skipped it as "still charging". So a subscription cancelled months ago stayed active with a next-billing date in the past. An ended or cancelled row was also re-activated on every run, even with no new charge. Both contradict D-65 ("no charge for two cycles plus 7 days marks it ended; a new charge reverses it"). Reported in AOS-516's Risks.

## Why
D-65, and the subscriptions page and dues (D-55) showing a subscription the owner already cancelled, with a renewal in the past.

## Scope
- **In:**
  - a detected group whose last charge is two cycles + 7 days old (in the user's zone) ends, with the existing `endedBy` / `endedReason` metadata;
  - an ended or cancelled row stays as it is until a charge after its `lastBilledDate`;
  - rows a broader detector saved before AOS-516 that today's rules reject end now, with a reason that says why (`Not a subscription: …`) instead of a wrong "No charge since …".
- **Out:** schema (no migration); the response DTO (metadata isn't exposed); a user "cancel" route (none exists).

## Acceptance criteria
- [x] A regular history that stopped more than two cycles + 7 days ago isn't active: a new row is saved `CANCELLED`, an active one is ended, both with no next-billing date and `endedReason = "No charge since <last>"`.
- [x] On the last day of grace it is still active; the day after, it is ended (weekly, monthly, quarterly, yearly, month ends and 29 Feb).
- [x] The boundary is judged in the user's zone, both behind and ahead of UTC.
- [x] An ended or cancelled row is not re-activated, or changed at all, until a charge after its last one; with one, it comes back `ACTIVE` with the ended keys cleared.
- [x] Newer charges that have also stopped update the row's charge data but keep it ended.
- [x] A live row whose merchant the AOS-516 rules reject ends with `endedReason = "Not a subscription: <reason>"` (e.g. "groceries, food or quick commerce", "the amounts vary"), other metadata kept, its charge history left as it was. Another user's row is not touched. If a later charge passes the rules, it comes back.
- [x] The eval set has stale cancelled histories (weekly, monthly, quarterly) and a late renewal in grace; the baseline is re-recorded.

## Design
- **Context:** detection runs nightly per user. Ending lived only in `endStopped`, which skipped every group the loop had just re-saved.
- **Options considered:**
  1. In the loop, judge each group by its last charge (`looksEnded`, D-65's rule shared with `endStopped`), and only re-activate on a newer charge. A stale group is still saved, as an ended row.
  2. Skip stale groups in the loop and let `endStopped` end them. Rejected: `endStopped` reads the stored `lastBilledDate`, which for a first detection doesn't exist, and a stale first detection would leave no row at all.
  3. Skip stale first detections entirely (save nothing). Rejected: the row is the history of a subscription the owner had, and a resubscription later reactivates the same row.
- **Rejected rows (AOS-516 false positives):** end at once with the rule's reason, rather than waiting for two cycles and then saying "No charge since …" while the charges continue.
- **Decision:** option 1, plus ending rejected rows at once. Proposed **D-136** (below).
- **Impact:** domain layer only (`SubscriptionDetectorService`). No route, schema, contract or web change.

### Proposed D-136 — Stale and rejected subscriptions end at once, reversibly
Type: Product · Tasks: AOS-517 · Builds on D-65, AOS-516 (proposed D-126)
- A detected charge history whose last charge is more than two cycles + 7 days ago (user's zone) is ended in the same run, saved as `CANCELLED` if it is new.
- An ended or cancelled subscription changes only with a charge after its last one, which re-activates it.
- A live row the subscription rules reject ends with `Not a subscription: <reason>`.
- Rejected: leaving stale groups to `endStopped` (no row or a stale date) and saving nothing for a stale first detection (loses the history).

## Implementation plan
1. `looksEnded(last, cycle, today)` in the companion; `endStopped` uses it.
2. In the loop: compute `charging`; a new or live row that isn't charging is saved/updated `CANCELLED` with no next date; an ended row without a newer charge is skipped.
3. Rejected groups end the merchant's live rows (`endNotSubscription`).
4. Tests, eval cases, baseline.

## Security (§4a)
- **Exposure:** none new. No route, input, upload, outbound call, secret, dependency or schema change. The detector runs in the existing nightly job over the owner's own transactions.
- **Abuse:**
  - A forged or replayed old charge can't re-activate an ended subscription unless it is dated after its last charge; a future-dated one would already be a new charge before this change, so this is no worse.
  - Ending is reversible and deletes nothing, so a wrong end costs a visible status, not data.
  - Rows are read and changed per user only (`findByUserId`, filtered by the merchant key); a test shows another user's row is untouched.
- **Logs:** subscription ID, the date and the rule's reason (a category word) only; no merchant name, amount or narration (D-33).
- **Tests:** boundary and hostile dates (last day of grace, the day after, month ends, 29 Feb, zones at UTC-10 and UTC+14), an old charge replayed after an end, a rejected merchant on another cycle.
- **Playwright:** no new screen, so no new spec.

## Risks / notes
- **Based on PR #140 (AOS-516), not merged yet.** Rebase onto `main` after #140 merges.
- A resubscription after a long gap shares the 400-day window with the old charges, so the gap can make the whole history irregular (no cycle) until the old charges age out; the row then stays ended a little longer. This was already so before (it is how the cycle is read); not changed here.
- Rows ended "Not a subscription" keep their old `lastBilledDate` on purpose, so a later accepted charge is recognised as new.
