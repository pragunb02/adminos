## Description
`WhatsAppExportFile` capped chat text at 10 MB per entry and the zip at 10 000 entries, but not the bytes inflated
across all entries (AUD-20, [AUDIT-2026-10](../security/AUDIT-2026-10.md)). Skipping an entry with
`ZipInputStream` still inflates it, so a 20 MB upload of highly compressed "media" could make the API inflate
gigabytes (CPU), and many text entries could each be read up to 10 MB.

## Why
Availability (CPU) on an owner-only upload: Low, CVSS 2.7. Defence in depth for a stolen session (T3) or a hostile
file the owner is tricked into uploading.

## Scope
- **In:** one budget per zip, across every entry (kept, skipped, media, metadata): inflated bytes and wall time.
- **Out:** the 20 MB upload cap and the 10 MB chat text cap (unchanged); plain `.txt` uploads (not inflated).

## Acceptance criteria
- [x] A zip whose entries inflate to more than 64 MiB in total is refused with 413 `FILE_TOO_LARGE`, wherever the bytes hide (media, many text files, macOS metadata). — `a zip bomb hidden in media …`, `many text entries …`, `the total counts skipped media …`, route `a zip bomb hidden in media is 413 and imports nothing`
- [x] Unpacking that takes longer than 5 s is refused the same way. — `unpacking that takes longer than the time limit is stopped` (injected time source, no sleeps)
- [x] A normal export with photos inside the limits still imports. — `an export with photos within the limits is still read` and the existing tests
- [x] Limits are validated. — `the limits must be positive`

## Design
- **Context:** `chatFromZip` read entries with `ZipInputStream`; non-text entries were skipped by `nextEntry`, which inflates them to find the next header.
- **Options considered:** 1) Parse the central directory and trust its sizes: the sizes are attacker-written. 2) **Drain every entry ourselves in 64 KiB chunks and charge each chunk to one budget** (chosen): it counts real inflated bytes. 3) Inflate on a separate thread with a timeout: needs cancellation and leaks a busy thread.
- **Decision:** `ZipLimits(maxInflatedBytes = 64 MiB, maxDuration = 5 s, timeSource)` injected into `WhatsAppExportFile.text`; a per-zip `Budget` checks bytes and elapsed time after every chunk and before every entry. Only the chat (or the first text file) is kept; other entries are inflated into the budget and dropped.
- **Patterns:** parameter object for limits; injected time source (deterministic tests, ENGINEERING §3).
- **Impact:** API only, `domain/ingestion/whatsapp`. No schema, contract or web change (the web already shows `FILE_TOO_LARGE`).

## Security (threat review, ENGINEERING §4a)
- **Exposes:** nothing new. It narrows the work one upload can cause.
- **Abuse and what stops it:**
  - a deflate bomb in a media entry → stopped at 64 MiB inflated, before the chat is reached;
  - many entries each under 10 MB → the total, not the per-entry cap, stops them; the 10 000-entry cap still holds;
  - slow inflation (many tiny entries, pathological streams) → the 5 s wall-time check before each entry and after each chunk;
  - lying sizes in the zip headers → never trusted; real bytes are counted.
- **Fail closed:** every limit breach and every `IOException` is a refusal; nothing is imported.
- **Privacy:** error messages never quote the file (D-33).
- **Tests that attack it:** unit (bomb in media, many text entries, metadata entries, slow unpack, limit validation) and a route test (413, nothing imported). The route was already authenticated and in the route inventory; no new screen, so no Playwright spec.

1. `ZipLimits` + `Budget`; drain entries in chunks. 2. Unit and route tests.
