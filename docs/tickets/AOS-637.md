## Description
The Go worker's start-up line `Database: …` used `maskPassword`, which printed the first 20 characters of
`DATABASE_URL`. That always includes the user name and, with a short user name, part or all of the password
(e.g. `postgresql://u:secret@…` is fully exposed in 20 characters). When the pool couldn't be set up, the worker also
logged pgx's error, which quotes the connection string (pgx masks the password but keeps the user name).

## Why
§2 Logging and §4a check 3: no secrets in logs. Container logs are read by anyone with Docker access on the host and
are shipped to wherever logs go.

## Scope
- **In:** the worker's database logging; a review of every worker and API log line for URLs, tokens or emails.
- **Out:** the worker's `Redis: <REDIS_URL>` line (AOS-634, PR #122, replaces it with host:port only; on `main`
  Redis has no password, so the URL holds no secret yet); API logging (AOS-628, PR #125: JDBC URL redaction,
  OIDC exception text, query strings).

## Acceptance criteria
- [x] The worker logs the database as `host:port/database` only, read with pgx's own parser (URL and key=value
      forms, multi-host, unix sockets); no user name, password or parameters, ever.
- [x] A malformed URL whose password has an unescaped `@`, `/`, `?` or `#` (so the parser would read part of the
      user info as host, port or database) logs a fixed "looks malformed" message, not any part of it.
- [x] A database name equal to the user name is shown as `(named after the user)`.
- [x] An unparseable value logs a fixed message; the parse error (which quotes the value) is never logged.
- [x] Pool set-up failure logs the safe target only, not pgx's error.
- [x] Host and database names are reduced to log-safe characters (no newline, space or bidi tricks to forge lines).
- [x] `maskPassword` removed.

## Design
- **Options considered:** 1) mask the password with a regex on the URL; 2) parse with `net/url`;
  3) parse with `pgconn.ParseConfig` (what pgx dials) and print only host, port and database, plus a pre-check that
  refuses user info outside the authority.
- **Decision:** 3. Option 1 misses DSN form and odd passwords; option 2 disagrees with pgx on DSNs and on where user
  info ends. A pre-check is still needed because both parsers misread an unescaped `/`, `?`, `#` or a second `@`.
- **Where:** `internal/config/database_target.go` (`config.DatabaseTarget`), a new file, so it doesn't conflict with
  AOS-634's changes to `config.go`.

## Security (D-100 §4a)
- **Exposes:** nothing new; removes credentials from logs.
- **Abuse and what stops it:** someone who can read the container logs learns the DB user or password → only
  host:port/database is printed; a malformed URL that would put user-info fragments in the host or database → fixed
  message; a crafted database name with `%0A` forging a log line → characters reduced to a safe set.
- **Tests (unit, hostile input):** URL, key=value DSN, password and user in the query, percent-encoded password,
  multi-host, TLS fallback not counted as a host, unix socket, empty and blank; malformed URLs with unescaped `@`
  `/` `?` `#`, a second `@` in the user name, bad port, broken IPv6, unterminated DSN quote, wrong scheme, garbage:
  none shows the user or password; log-line forging; bidi and tab characters. No route or screen, so no route or
  Playwright attack spec applies. Test credentials are built at run time (no literal connection string with a
  password in the source, so GitGuardian has nothing to flag).

## Log review (other worker and API logs)
- **Worker:** Gmail client errors never quote Google's response body (`checkResponse` drains it); connection, user
  and job IDs are UUIDs; no token, email address or message text is logged. Found, not fixed (out of this task's
  step): the bridge logs the job `type` read from Redis with `%s` (`[bridge] Failed to enqueue %s`), so a value with
  a newline could forge a log line. Only the API writes that list; suggested follow-up: `%q`. Also,
  `config.Load` defaults `DATABASE_URL` to a dev URL with a dev password when unset (a silent fallback, §2).
  Suggested follow-up: no default outside dev mode.
- **API:** `DatabaseFactory` logs the full JDBC URL and two places log OIDC exception text; both are fixed by
  AOS-628 (PR #125). Push endpoints are logged through `PushEndpoint.toString()`, which returns only the push service
  origin. No other log line with URLs, tokens or emails was found.
