## Description
`ExposedBillRepository.findUpcoming` (both) and `findOverdue` used `LocalDate.now()`, the JVM's zone and the wall clock.
`InMemoryBillRepository` defaulted to `Clock.systemDefaultZone()`, and so did `dashboardRoutes`. So, on a UTC server,
from 18:30 to 24:00 UTC:
- "upcoming" still included bills due yesterday in India;
- `/bills/upcoming` and the dashboard used a different day from the reminder engine;
- the Exposed and in-memory repositories could disagree.

Also, `AppConfig.redis.url` was read but never used: the queue wiring reads `REDIS_URL` itself.

## Why
ENGINEERING §2 and §3: tests are deterministic, `Clock` is injected, and the user's dates come from `UserCalendar`
(ReminderEngine already works this way). D-78: India first, but the date is always the user's own.

## Scope
- **In:** `BillRepository` date queries, `BillTrackingService`, `ReminderEngine` (call sites only), `dashboardRoutes`'
  clock, `AppConfig.redis` / `RedisConfig` and the unused `adminos.redis` block in `application.conf`.
- **Out:**
  - `DuesRoutes` and `MandateRoutes` use `LocalDate.now(principal.zone)`. That's the user's zone, so it doesn't depend
    on the JVM zone, but the clock isn't injectable; suggested follow-up.
  - `InMemoryBillRepository.update` and `ExposedBillRepository.update` stamp `updatedAt` with `Instant.now()`
    (an instant, not zone-dependent).
  - The rest of the `adminos { … }` block in `application.conf` also looks unread (`AppConfig.load()` reads the
    environment). Reported, not removed.
  - AOS-634's Redis changes (#122).

## Design
- **Options considered:**
  1. Inject a `Clock` into `ExposedBillRepository` (like the in-memory one). That fixes the wall clock, but the
     per-user query still uses one zone for everyone, and persistence would be deciding what "today" means.
  2. Have the repository call `UserCalendar`. That breaks the layer rule (persistence calling a domain service).
  3. Repositories take the date; the domain decides it via `UserCalendar`, either the user's date or the server's
     date for cross-user pre-filters that are then refined per user.
- **Decision:** 3 · **Pattern:** dependency inversion of time: the domain owns the calendar, and persistence filters
  on what it's given.
- **D-123 (Architecture, recorded in DECISIONS.md):** repositories never read the clock or a zone. Callers pass dates from
  `UserCalendar` (`today(userId)` for one user, `serverToday()` for cross-user pre-filters refined per user).
  Rejected: a clock in each repository, and repositories calling `UserCalendar`.
- **Impact:**
  - `BillRepository` interface (both implementations);
  - `BillTrackingService` constructor (+ `UserCalendar`, wired by Koin);
  - `ReminderEngine` call sites, `dashboardRoutes` signature, `FinancialModule`, `AppConfig`.
  - No schema or API contract change.
