## Description
A **habit lens** is a named group of spending the owner wants to watch: quick commerce, food delivery, nights out, shopping, pay-later and travel. Each lens is data: the brands, categories, subcategories and keywords that belong to it. The defaults live in one file; the owner can add a merchant to a lens or take one out, and that choice is remembered.

The merchant catalogue gains the brands the lenses need (Flipkart Minutes, BB Now, Amazon Now, LazyPay, Simpl, Amazon Pay Later, SpiceJet, AbhiBus, ixigo and others), without lowering the categorisation golden-set floor (D-61).

## Why
D-80: the coach shows where money leaks. "Leaks" are habits, not categories: Swiggy Instamart is groceries in the catalogue but a quick-commerce habit; a bar can be Food or Entertainment. Lenses give every later E9 task (leaks page, limits, digest, report card, goals) one shared definition. BRD §5.6.

## Scope
- **In:**
  - `resources/coach/lenses.json`: six default lenses and the late-night window, validated on load against the merchant catalogue (a bad file fails startup, like D-44).
  - Matching rules as small strategies (brand, category, subcategory, keyword) and a user override (add or remove a merchant).
  - **Person-to-person UPI payments never count in a lens** (they are mostly settle-ups with friends, e.g. after splitting a bill), unless the owner adds that payee by hand.
  - Only spending and refunds count (D-39): a refund nets off its lens; transfers, reversals and income never match.
  - `lens_overrides` table, repository (in-memory + Postgres), service, routes:
    - `GET /api/v1/coach/lenses`: the lenses with their rules and the owner's overrides;
    - `PUT /api/v1/coach/lenses/{lens}/merchants`: `{ "merchant": "…", "include": true|false }`;
    - `DELETE /api/v1/coach/lenses/{lens}/merchants?merchant=…`: back to the default.
  - Catalogue additions with tests; golden-set gate green.
- **Out:** the leaks numbers and page (AOS-902); editing lens rules other than per-merchant overrides; new lenses from the UI (a new lens is one JSON entry).

## Acceptance criteria
- [x] The six default lenses load from `lenses.json`; an unknown brand, category, duplicate id, short keyword or bad late-night window fails loading with a message naming it.
- [x] Quick commerce matches Zepto, Blinkit, Swiggy Instamart, BB Now, Flipkart Minutes, Amazon Now; food delivery matches Swiggy, Zomato and any `food_delivery` subcategory; nights out matches bar/pub/club keywords and nightlife brands; shopping, pay-later and travel match their brands and subcategories.
- [x] A person-to-person UPI payment (personal handle, no merchant hints, not a catalogue brand) is in no lens, even when its category or name would match; merchant QR handles (Paytm QR, PhonePe `Q…`, BharatPe, Razorpay…) are not treated as people.
- [x] The owner can add a merchant to a lens (it then matches, even a person) or remove one (it never matches that lens); deleting the override restores the default. Overrides are per user, case-insensitive, and survive restarts (Postgres).
- [x] Transfers, reversals and income never match a lens; refunds match like the spending they reverse.
- [x] Catalogue additions are categorised as expected, and `./gradlew -q categorizationReport` plus the regression test pass.
- [x] Routes: 401 without a session; 404 for an unknown lens; 400 for a blank or over-long merchant.

## Design
- **Context:** the catalogue (D-44) knows brands and their default category; the categoriser (D-41) decides category and subcategory, and corrections are remembered per payee. Nothing groups spending by habit. P2P payments are categorised Other (D-41) but can be re-labelled by the owner, so a category rule alone could pull a settle-up into a lens.
- **Options considered:**
  1. **Lenses as categories/subcategories only** (e.g. "quick commerce" = subcategory `quick_commerce`): changes the categoriser and the golden set, mixes "what it is" with "what habit it feeds", and an Instamart order can't be both groceries and quick commerce.
  2. **Hard-coded lens classes in Kotlin**: precise, but a new app is a code change (against D-44/D-80).
  3. **Lenses as data, matched by small rule strategies, plus per-merchant overrides** (chosen). The file says *which* brands, categories, subcategories and keywords; four rule types say *how* to match; the owner's overrides sit on top.
- **Decision:** option 3. **Patterns:** Specification (one `LensRule` per kind), Registry (`LensCatalogue` loaded and validated like `MerchantCatalogue`), Repository (`LensOverrideRepository`, in-memory + Exposed).
  - **Match order** for one transaction and lens: not spending/refund → no; owner removed this merchant → no; owner added it → yes; person-to-person → no; any rule matches → yes.
  - **Brand rule** compares the normalised merchant name with catalogue brands (case-insensitive), so it follows the normaliser (D-44). **Keyword rule** is whole-word on the merchant name in catalogue matching form.
  - **Person-to-person** (`PersonToPersonRule`): a UPI payee whose handle is a personal PSP handle (`@okaxis`, `@oksbi`, `@ybl`, `@paytm`, … or a 10-digit mobile number) and whose name is not a catalogue brand, with no merchant hint in the handle (`paytmqr`, `bharatpe`, `Q…@ybl`, `gpay-…`, `rzp`, `payu`, `merchant` …). Rejected alternative: treat every Other-category UPI payment as P2P (it would hide small bars and kiosks).
  - **Overlap:** a transaction may sit in two lenses (Amazon Pay Later is pay-later and could be shopping); totals across lenses use the union (AOS-902).
- **Extensibility:** a new habit is one JSON entry; a new app is one catalogue entry plus its brand in a lens; a new match kind is one `LensRule` class.
- **Impact:** new `domain/coach` package (own Koin module included by `AppModule`, own route module), `V31__lens_overrides.sql`, catalogue data. No change to the categoriser or the pipeline.

## Security (D-100, docs/ENGINEERING.md §4a)
- **What it exposes:** three authenticated routes under `/api/v1/coach/lenses` (one read, two mutations); one new table holding merchant names the owner typed; a data file shipped in the jar. No outbound calls, jobs, secrets or new dependencies.
- **Abuse and what stops it:**
  - *Stranger / signed out:* every route sits in `authenticate("auth-jwt")` → 401 (tested for GET, PUT and DELETE). A forged or tampered token is refused (tested).
  - *Cross-site request (CSRF):* the session cookie is `SameSite=Strict` (existing design, `Authentication.kt`), so a cross-site form or fetch carries no session → 401. The API has no Origin check of its own; that is AOS-619's scope.
  - *Another user's data:* overrides are keyed by the token's user id; there are no resource ids to guess. One user's overrides never show for another (tested).
  - *Hostile input:* the merchant is trimmed and bounded (1..255, else 400); SQL injection strings, `<script>`, a right-to-left override character, path-like text and emoji are stored as bound parameters and returned as JSON strings, never interpreted (route + Postgres tests). Lens ids are validated against the shipped file (`..%2F..` → 404). Malformed JSON → 400. Keywords are regex-escaped, so lens data can't inject a pattern (tested), and a 100,000-character merchant name is matched without trouble.
  - *Bad data file:* validated at startup (fail closed): unknown brand/category, duplicate id, short keyword or bad window refuses to start.
- **Data at rest:** merchant names the owner chose for their own lenses; not sensitive beyond what `transactions.merchant_name` already holds (same protection). No raw message text (D-33). Nothing logged.
- **Listeners / dependencies:** none added.
- **Playwright:** no new screen in this task (the leaks page and its attack spec come in AOS-902).

## Risks / notes
- Keyword rules can over-match ("club", "lounge"); the owner removes a merchant with one call, and the leaks page (AOS-902) shows every merchant in a lens so it's visible.
- The P2P rule is a heuristic; a misjudged merchant is fixed by adding it to the lens.
