## Description
A stolen Google session alone must not open AdminOS (AUD-09). After Google, a passkey is required for a full session.
Enrolment on first sign-in, hashed recovery codes, and a bootstrap that can't lock the owner out. Runbook:
[docs/security/PASSKEYS.md](../security/PASSKEYS.md).

## Acceptance criteria
- [x] A Google sign-in creates a **pending** session; every app route answers `401 AUTH_010` until a passkey (or recovery code) confirms it; only `/api/v1/auth/passkey/*` accept it. Refresh keeps it pending.
- [x] **Enrolment:** with no passkey, the pending session may enrol the first one, which confirms it and returns 10 recovery codes once. Later passkeys only from a confirmed session.
- [x] **Verification:** user verification required; origin and RP ID exactly `APP_URL`'s; challenge single-use and 5 min; signature counter must not go backwards.
- [x] **Recovery codes:** 80-bit Crockford base32, SHA-256 at rest, single use (atomic), regenerate from a confirmed session only; use alerts the owner.
- [x] **Limits:** 5 failed attempts per session → session revoked + alert. Response JSON ≤ 64 KB; bodies capped (AOS-615).
- [x] **Alerts:** passkey added, recovery code used, checks failed (via the AOS-620 port).
- [x] **Web:** `/auth/passkey` (enrol → codes → home; verify; recovery code; sign out), callback routes there, any `AUTH_010` sends the browser there; Settings → Security lists passkeys, adds one, makes new codes.
- [x] **Playwright** with Chromium's virtual authenticator (enrol, verify, UV refused, AUTH_010 redirect); WebKit limits documented.
- [x] Library: licence and release recency verified (Yubico java-webauthn-server 2.10.1, BSD-2-Clause, 2026-10-09; OSV clean).

## Design
- **Library options:** 1) **Yubico java-webauthn-server** (chosen: maintained by a FIDO member, BSD-2-Clause, release 2026-10-09, full L2 verification incl. counters); 2) WebAuthn4J (Apache-2.0, also good; more configuration for the same checks); 3) hand-rolled verification (rejected: CBOR/COSE/signature/flag rules are easy to get subtly wrong).
- **Session model options:** 1) **a pending state on the session (`second_factor_at`) checked by the per-request session gate (AOS-620) with a second auth provider for the passkey routes** (chosen: one place decides, access tokens need no new type, revoke still works); 2) a separate short "pre-auth" token type (another token to secure and rotate); 3) delay issuing any session until the passkey (needs Google's code and the passkey in one request, awkward UX and state).
- **Bootstrap options:** 1) **first-enrolment-wins on a pending session, alerted, documented server-side reset** (chosen); 2) a one-time enrolment secret printed at start-up (safer against a stolen Google session before first use, but one more secret to handle for a single user — revisit if the app is ever reachable before the owner's first sign-in); 3) allow enrolment from any session (rejected: a stolen Google session could add its own passkey).
- **Ceremony state:** in memory per session, 5-minute TTL (single instance; a restart just means "start again").
- **Patterns:** port + adapter (`WebAuthnCeremonies` ← `YubicoWebAuthn`), repositories with InMemory + Exposed implementations.

## Security (D-100 §4a)
- **Exposes:** seven routes under `/api/v1/auth/passkey` (provider `auth-pending`, CSRF-checked, reviewed in the route inventory); tables `webauthn_credentials` (public keys), `recovery_codes` (hashes); `sessions.second_factor_at`. Migration V62 (tentative). One dependency (Yubico, BSD-2-Clause) and its transitive set, OSV clean.
- **Abuse and what stops it:** stolen/phished Google session → pending only; adding an attacker passkey → refused once one exists; forged/replayed/cloned assertions → library checks + single-use challenge + counter; brute-forcing codes → 80 bits + 5-attempt revoke; verification details → logged, never returned.
- **Tests:** unit with a software authenticator (all forgeries), route (full HTTP flows, AUTH_010, CSRF, size), integration (V62 on Postgres, concurrent code use), web unit (pages, helpers), Playwright (virtual authenticator).

## Proposed decision D-96 — Google + passkey, always (Type: Architecture / Security)
- A session is full only after a passkey (user verification required) or a one-time recovery code; until then only the passkey step is reachable (`AUTH_010` elsewhere).
- RP ID = `APP_URL` host, origin = `APP_URL` origin; Yubico java-webauthn-server verifies; no attestation.
- First passkey: enrolled from the first pending session (alerted); later ones only from a confirmed session. Ten recovery codes (80-bit, SHA-256), regenerable from a confirmed session. Reset only server-side (runbook).
- Five failed attempts end the session and alert.
- Rejected: TOTP (phishable), SMS codes, optional second factor, hand-rolled WebAuthn.

## Risks / notes
- **Owner actions:** do the first sign-in yourself right after deploying; save the recovery codes; add a second passkey. Changing `APP_URL` invalidates passkeys (reset per runbook).
- Dev mode (in-memory) accepts tokens without a session (tests); with a database every session needs the passkey.
- Passkey deletion isn't offered yet (deleting the last one would reopen the bootstrap); add with a "keep at least one" rule if needed.
