## Description
Redis ran with no password. Anything that reached it (another container on the compose network, a process
on the host through `127.0.0.1:6379`, or a browser page doing DNS rebinding against the loopback port) could
read and write the job queue: queue Gmail syncs for any user id, or read job payloads. The Go worker also
logged `REDIS_URL` in full at start-up, and parsed it by hand, ignoring any password in it.

## Why
D-91: owner-only, defence in depth. Loopback-only publishing (AOS-616) stops other machines, not other
local processes or containers.

## Scope
- **In:** `requirepass` in compose from `REDIS_PASSWORD`; the API and workers get it (as `REDIS_PASSWORD`
  beside `REDIS_URL`, or inside a host-run `REDIS_URL`); both refuse to start without it; the worker uses
  `asynq.ParseRedisURI` and never logs the URL; `.env.example`; tests.
- **Out:** Redis ACL users, TLS between containers (same host, private network), rotating the password.

## Design
- **Context:** the API (Lettuce) builds its client from `REDIS_URL` only when it is set; the worker used
  `parseRedisAddr` (host only) and printed the URL.
- **Options considered:**
  1) Password spliced into `REDIS_URL` in compose (`redis://:` + `${REDIS_PASSWORD:?}` + `@redis:6379`), as
     the bug report suggested. **Tried and rejected:** GitGuardian flags each such line as a "Generic
     Password" (3 incidents on the first push of this PR), which blocks the merge gate, and a password in a
     URL needs escaping.
  2) **`REDIS_PASSWORD` beside a bare `REDIS_URL`** (as Postgres uses `PGPASSWORD`), read by the API and the
     worker; a host-run client may instead put the password in the URL's user info (the libraries' own
     parsers read it); if both are set they must agree.
  3) For the server: `--requirepass` on the command line (visible in `ps` and `docker inspect`), a generated
     config file (needs a writable path, which AOS-622's read-only root filesystem removes), or **stdin**.
- **Decision:** 2 for clients, stdin for the server. `.env.example` says `openssl rand -hex 32` (the value is
  written unquoted into Redis's config line). Fail fast: both clients refuse to start without it (proposed D-103).
- **Patterns:** fail closed; secrets never logged (only `host:port`); fixed error values that don't quote input.
- **Impact:** compose, API DI wiring, worker start-up; no schema or contract change.

## Security (threat review, ENGINEERING §4a)
- **Exposes:** nothing new. It closes an unauthenticated datastore.
- **Abuse and what stops it:**
  - another container or local process, or a DNS-rebinding page against `127.0.0.1:6379` → NOAUTH without
    the password (tested from the compose network and from the host);
  - the password leaking through logs → the worker logs only `host:port`; the API's start-up errors and the
    worker's errors are fixed strings; Lettuce's URI text has no password (tested);
  - leaking through process listings or `docker inspect`'s Cmd → stdin, not arguments (checked); the value is
    in the container's environment, readable only by root on the host or by Docker's users (already
    root-equivalent);
  - a weak or empty password → compose refuses an empty one; `.env.example` gives a 256-bit hex recipe;
  - misconfiguration silently running without auth → both clients refuse to start without a password, and
    refuse two different ones rather than picking one.
- **Checks:** no literal secrets (tests build random passwords at run time; compose uses the variable); no
  new dependency; no bind widened (`check-compose-exposure.sh` and its test green).

## Risks / notes
- **Owner action:** add `REDIS_PASSWORD=` followed by the output of `openssl rand -hex 32` to `.env` before
  the next `docker compose up` (compose refuses to start without it). A host-run API or worker reads the same
  `REDIS_PASSWORD`.
- **GitGuardian:** the first push of this branch put the password variable inside three `REDIS_URL` lines and
  GitGuardian raised 3 "Generic Password" incidents (no real secret: the lines held only `${REDIS_PASSWORD:?}`).
  The branch was rewritten to one commit without them; the incidents may need to be marked false positive in
  the GitGuardian dashboard.
- **Merge with AOS-622 (PR #105):** both edit the `redis` service. Keep #105's hardening (`<<: *hardened`,
  `user`, `networks`, `volumes`, limits) and this PR's `environment`, `command` and `healthcheck`; #105's
  `hardened-stack.smoke.sh` and CI then need `REDIS_PASSWORD` set (a random value per run).
- Found, not fixed: the worker's `maskPassword` prints the first 20 characters of `DATABASE_URL` (compose
  passes no password in it, but a host-run URL could); `AppConfig.redis.url` is read but never used.

## Resolution
Redis requires `REDIS_PASSWORD` (stdin, never an argument); every client gets it beside a credential-free
`REDIS_URL` (or inside a host-run URL); the API (`RedisUrl`) and the worker (`redisconn`, on
`asynq.ParseRedisURI`) refuse to start without it and never log the URL or the password. Verified by unit, Testcontainers, child-process and compose smoke tests. Actual 2h vs ETA 2h.
