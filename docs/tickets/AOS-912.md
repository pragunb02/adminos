## Description
The "Pay later" habit lens (AOS-901, D-81) matched spends by provider brand (LazyPay, Simpl…) or the `pay_later` subcategory. After AOS-909 (D-89), a pay-later purchase is a spend **at the merchant** with `paymentMethod = pay_later`, and the bank repayment to the provider is a **transfer** (`pay_later_bill`). The lens therefore matched almost nothing, and the few rows it did match were repayments that hadn't been recognised as transfers, which would count the money twice.

This task makes the lens match purchases by how they were paid.

## Why
The lens is meant to show how much the owner buys on credit (D-81). Counting repayments instead of purchases counts the same money twice (D-39, D-89).

## Scope
- **In:**
  - a `paymentMethods` rule kind for lenses (data, validated on load like the others);
  - the shipped `pay_later` lens uses only `paymentMethods: ["pay_later"]`, with no provider brands and no `pay_later` subcategory;
  - `GET /coach/lenses` lists each lens's `paymentMethods`;
  - tests.
- **Out:**
  - the web rule summary on `/leaks` ("Counts …"). It lives on `main` (AOS-902) and isn't on this branch's base. See Risks.
  - no schema change.

## Acceptance criteria
- [x] A purchase with `paymentMethod = pay_later` lands in `pay_later` at any merchant, and also in its own lens (e.g. Zepto → quick commerce + pay later). Totals across lenses use the union (AOS-901), so it's counted once.
- [x] A card or UPI purchase is not in `pay_later`.
- [x] A repayment to a provider is in no lens, both as a transfer (D-89) and when it's still a spend because it wasn't recognised.
- [x] A pay-later refund nets off the lens (D-46).
- [x] An unknown payment method in the lens file fails start-up with its name. An empty rule is refused.
- [x] End to end (SMS purchase + bank repayment through the pipeline): exactly one row is in the pay-later lens.

## Design
- **Context:** lenses are data (D-81); each rule kind is a small `LensRule` class.
- **Options considered:**
  1. A `PaymentMethods` rule kind in the lens file. Chosen.
  2. Hard-code a special case for `pay_later` in `LensMatcher`. Rejected: a special case in code, against D-81.
  3. Keep the brands and add the method. Rejected: the brands only ever match repayments, which is the double count.
- **Decision:** option 1. **Patterns:** Specification (one more `LensRule`).
- **Extensibility:** any lens can now say "paid by wallet / cash / credit card" with one field.
- **Impact:** `HabitLens.kt` (rule), `LensCatalogue.kt` (load and validate), `LensRoutes.kt` (DTO field), `coach/lenses.json`. No schema or route change.

## Security (§4a)
- **Exposure:** none new. One more read-only field on an existing authenticated route (`GET /coach/lenses`). No new input from users: the rule comes from the shipped lens file.
- **Abuse:** a forged SMS can't move money into or out of the lens beyond what AOS-909 already accepts. The payment method comes only from the provider-SMS and provider-email parsers that AOS-909 reviewed. A typo in the lens file fails start-up instead of silently matching nothing (unit test).
- **Tests:** unit tests (rule, validation, unknown method, empty rule); route test (field listed, providers not listed); the existing route auth and hostile-input tests in `LensRoutesTest` still pass. No new screen, so no new Playwright spec.
