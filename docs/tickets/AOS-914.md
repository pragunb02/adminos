## Description
D-111 (AOS-911, PR #126) adds `transactions.own_share` and `Transaction.countedAmount` (the share when the bill was split, else the amount). The console's analytics already sum `countedAmount`. The coach didn't:
- `LeakCalculator` (AOS-902), `Limits` / `LimitService` / `LimitAlerts` / `LimitSuggester` (AOS-904), goals (AOS-907), the report card (AOS-906) and the savings projection (AOS-908) all read `LeakFact.amount` / `LeakFact.signed`;
- and `LeakFact.amount` was `transaction.amount`.

So a ₹4,000 dinner where the owner's share is ₹1,000 counted ₹4,000 in the leaks and pushed limit alerts at ₹4,000.

## Why
- The coach exists to make careless spending visible (D-80). Counting friends' parts of a bill overstates the habit and fires pushes that aren't true.
- D-45 / D-46: every number agrees with every other. Analytics said ₹1,000; the leaks said ₹4,000.

## Scope
- **In:**
  - one definition of what a transaction counts as, used by every coach number;
  - tests across leaks, limits (status, push, suggestion), goals (progress, cut baseline, streak) and the savings rate and projection, for a split bill and for settlements both ways;
  - a Postgres test of the same read path.
- **Out:**
  - analytics (already counts the share, #126);
  - anomaly detection and subscription detection: they look at what the bank charged, not at the owner's spending (see D-139);
  - the web: the leaks drill-down still lists the bank's amount; `ownShare` is in `TransactionResponse` since #126, and the web feed shows it (#128).

## Acceptance criteria
- [x] Leaks: a split bill adds the share to spent, ordered, average order, late night, weekdays and the merchant row (`SplitShareTest`).
- [x] The drill-down lists the split bill once, and settlements never (`SplitShareTest`).
- [x] Limits: status, the 50/80/100% pushes (title and body) and suggested limits use the share; settling up moves nothing (`SplitShareTest`).
- [x] Goals: progress, the frozen cut baseline and no-spend streaks use the share; settlements are not orders (`SplitShareTest`).
- [x] Savings: the month's spent and rate use the share, settlements are neither income nor spend, and "what leaks could become" projects the share (`SplitShareTest`).
- [x] A bill paid only for friends (share ₹0) counts ₹0 everywhere and pushes nothing (`SplitShareTest`).
- [x] Postgres and the in-memory fake agree, and the leaks total equals the analytics' spend for the same transactions (`CoachSplitShareIntegrationTest`).
- [x] No second definition: `LeakFact.amount` is `Transaction.countedAmount`; no calculator reads `transaction.amount` (grep below).

## Design
- **Context:**
  - Every coach number is made from `LeakFact`s built by `LeakService.facts` (leaks, limits, goals, report card, savings projection).
  - The savings rate's income and spent come from analytics (D-87), which already sum `COALESCE(own_share, amount)` in SQL and `countedAmount` in memory.
  - `LensMatcher.COUNTED` (spend, refund) already leaves `settlement` out, and analytics count only spend, refund and income, so settlements were already excluded. The tests now pin that down.
- **Options considered:**
  1. **`LeakFact.amount` returns `transaction.countedAmount`** (one line, one place). Every calculator already reads `amount` or `signed`, so they all follow, including ones not yet written.
  2. **Change each calculator** (`LeakCalculator`, `Limits.spent`, `GoalMath`, `ReportCard`, `LimitSuggester`) to read `transaction.countedAmount`. That is five copies of the same rule, and the next calculator could forget it.
  3. **Rewrite `amount` in `LeakService.facts`** (copy the transaction with `amount = countedAmount`). That needs no new field, but `LeakTransactions` would then return altered transactions, so the drill-down would show a made-up bank amount. It also breaks `ownShare <= amount`.
- **Decision:** option 1 (proposes **D-139**). `LeakFact` is the coach's single view of a transaction, and `Transaction.countedAmount` is the console's single definition (D-111). **Patterns:** a value object with a derived property.
- **Extensibility:**
  - A new coach number built on `LeakFact` counts the share without doing anything.
  - If a future source changes what "counted" means (for example a reimbursed work expense), it changes `Transaction.countedAmount`, and analytics and the coach follow together.
- **Impact:**
  - `domain/coach/leaks/Leaks.kt` only; no schema change, no route change, no contract change.
  - A limit that already pushed at the full price before the share was imported keeps its claimed thresholds, like a refund (AOS-904: a drop below a threshold never re-arms it).

**Proposed D-139 (Architecture / Product, AOS-914):** every coach number counts `Transaction.countedAmount` through `LeakFact.amount`, the same definition analytics sum (D-111). Detectors that judge the bank's charge itself (anomalies, subscriptions, bill payment matching) keep `amount`.

## Security (threat review, ENGINEERING §4a, D-100)
**What it exposes:** nothing new. There are no new routes, inputs, uploads, outbound calls, stored data, secrets, jobs, dependencies or listeners. One derived property changes which stored number the existing owner-only coach routes sum.

**How it could be abused, and what stops it**
| Threat | Control | Test |
|---|---|---|
| A crafted Splitwise import lowers a share to hide spending from limits | Only the owner can import (AOS-911, auth and IDOR tests there). A share is bounded `0 ≤ share ≤ amount` by `Transaction.init`, and a share of 0 is shown as an order at ₹0, not hidden | `SplitShareTest` (share 0), AOS-911's `SplitServiceTest` |
| Settlements (money between friends) inflating leaks or the savings rate | `LensMatcher.COUNTED` and analytics' natures exclude `settlement` | `SplitShareTest`, `CoachSplitShareIntegrationTest` |
| Another user's transactions in the numbers | Unchanged: `LeakService.facts` reads by `userId` only | existing `IdorTest`, `LeakServiceTest` |
| Push text leaking data | Unchanged: deterministic text of amounts only (D-57); now the share instead of the bill | `SplitShareTest` (exact body) |

**Tests that attack it:**
- unit: share 0, refund of a split bill, settlements both ways, settlements under a lens's merchant name;
- integration: Postgres read path;
- route and Playwright: no route or screen changes, so the existing ones stand.

**Checks**
- [x] No secrets or personal data: synthetic merchants and names only.
- [x] No new listener, no dependency, no schema.
- [x] No AI.
