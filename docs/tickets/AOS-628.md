## Description
Make what the API logs safe by construction (AUD-24, [AUDIT-2026-10](../security/AUDIT-2026-10.md)):
- request lines without query strings or response headers;
- no library messages that carry caller-chosen text concatenated into logs;
- no statement values in database exception logs.

## Why
Query strings carry search terms, opaque cursors, and (on OAuth callbacks) codes and states. Ktor's default call line also appends the `Location` of a 302, which for "connect Gmail" is Google's consent URL with our single-use state. Nimbus' messages quote the token's claims, which whoever sends the token chooses (log injection). Postgres error details quote row values ("Key (email)=(…) already exists"). Low, CVSS 2.2.

## Scope
- **In:**
  - `CallLogging` format;
  - `OidcVerifier` and webhook logging;
  - `StatusPages` catch-all for SQL errors;
  - the JDBC pool's `logServerErrorDetail`;
  - the start-up database URL line.
- **Out:**
  - the `ConnectionService` plaintext warning (removed outright by AOS-629);
  - the Go workers and the parser (their logs already use format strings and codes only; checked).

## Acceptance criteria
- [x] Request lines show status, method, path (without the query string), time and request ID. They never show the query or the `Location` header. Tests: `request lines have the path but never the query string`, `a redirect's Location is never logged`
- [x] OIDC failures log the exception type only. The message passed on is fixed and never includes the library's text. Test: `a token for a different audience is rejected` (now asserts the fixed message)
- [x] An unhandled database error is logged as its type, SQLState and first app frame. Its message (and so its values) is never logged, even when wrapped. Tests: `a database error is logged by kind and SQLState …`, `other unhandled errors are still logged with their exception`
- [x] With the production pool, Postgres errors name the constraint but not the values. Test: `DatabaseErrorDetailIntegrationTest`. The existing duplicate-email tests still map by constraint name.
- [x] The start-up line logs the DB URL without user info or parameters. Test: `the database URL is logged without credentials or parameters`

## Design
- **CallLogging:**
  - an explicit `http` logger (tests read it) and a fixed `format`: `"<status> <METHOD> <path> in <ms>ms [<requestId>]"`;
  - `path()` drops the query, and no response header is written.
- **OIDC:** `logger.warn("… {}", e.javaClass.simpleName)`, and `OidcVerificationException("Invalid OIDC token", e)`. The cause is kept for debugging in code, but never logged.
- **StatusPages:** `sqlCause()` walks the cause chain. A SQL error is logged as `{type} (SQLState {state}) at {first dev.adminos frame}`; everything else is logged as before.
- **pgjdbc `logServerErrorDetail=false`:** the driver itself leaves Detail/Where (row values) out of exception messages. This covers Exposed's, Flyway's and Hikari's own logs too, which we don't control.
- **Options considered:**
  1. A logback masking pattern (regex over every line). It is fragile and misses new formats.
  2. **Remove the data at its source** (chosen).

## Security (threat review, ENGINEERING §4a)
- **Exposes:** nothing new. This reduces what logs contain.
- **Abuse and what stops it:**
  - search terms, cursors, OAuth `code`/`state` in URLs → the path only;
  - a consent URL with our state in a redirect's `Location` → never logged;
  - a forged push token with newline-laden claims (log injection) → only the exception type is logged;
  - a duplicate-key or not-null error quoting an email, an amount or a merchant → the driver omits the detail, and the error handler logs only the type and SQLState;
  - a DB URL with credentials or parameters → redacted.
- **Tests that attack it:**
  - unit and route tests with a log capture (logback `ListAppender`) on the real loggers;
  - an integration test on real Postgres with the production pool settings.
  - No route and no screen, so no Playwright spec.
