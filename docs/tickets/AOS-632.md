## Description
`apps/web/Dockerfile`'s runtime stage copied `.next`, `node_modules`, `package.json` and `next.config.mjs`
but never `public/`, so in the container `/sw.js`, `/icon-192.png` and `/icon-512.png` were 404. Without
the service worker, Web Push (AOS-510) can't register; the Home Screen app has no icon. (The manifest is
generated from `src/app/manifest.ts`, so it was served.)

## Why
Bug found in review: the PWA and Web Push only worked under `next dev` / `next start` on the host.

## Scope
- **In:** copy `public/` into the runtime stage; a script that checks a built image serves the PWA files,
  and a test for that script.
- **Out:** wiring the script into CI (AOS-622, PR #105, can add it as a step); Playwright.

## Acceptance criteria
- [x] The runtime image contains `public/`. → `apps/web/Dockerfile`
- [x] A check builds (or takes) the image, runs it with no secrets, no network and no published port, and
  fails unless `/sw.js`, `/manifest.webmanifest`, `/icon-192.png`, `/icon-512.png` and `/apple-icon.png`
  answer 200 with the right content type, without following redirects, and the `public/` files match the
  repo's bytes. → `scripts/check-web-image.sh`
- [x] The check fails closed: 404, a redirect to `/login`, other bytes, a wrong content type, a server that
  never answers, a failed build or run; the container and a throwaway image are always removed.
  → `scripts/tests/check-web-image.test.sh` (13)

## Design
- **Context:** Next serves `public/` from the working directory at runtime; `proxy.ts` already lets these
  paths through without a session (AOS-510).
- **Options considered (check):** 1) a shell script that runs the image isolated and probes from inside;
  2) a CI-only step with `curl` against a published port (needs a host listener and only runs in CI).
- **Decision:** option 1, usable locally and from CI. **Patterns:** fail closed; test doubles for `docker`.
- **Impact:** the web image only; no API, schema or contract change.

## Security (threat review, ENGINEERING §4a)
- **Exposes:** five static files that were meant to be public already (`PUBLIC_FILES` in `proxy.ts`). They
  hold no data or secrets: a service worker, icons and a manifest. `public/` has nothing else in it; the
  build context's `.dockerignore` keeps `.env*` out of the image, so copying `public/` can't carry one in.
- **Abuse and what stops it:** a stranger can't reach the site at all (tailnet only, D-91); a signed-out
  browser gets only these files, every other path still redirects to `/login`.
- **The check itself:** the container gets no `.env`, no environment, `--network none`, all capabilities
  dropped and `no-new-privileges`; no port is published, so it adds no listener even while it runs. The
  test asserts that the fake `docker run` never receives `-p`, `--env-file` or `-e`, and always gets
  `--network none`.
- **Checks:** no new dependency; no literal secrets; no bind widened (`check-compose-exposure.sh` green).

## Verification
- Before the fix: `scripts/check-web-image.sh` → `FAIL /sw.js: status 404`, icons 404, exit 1.
- After: `scripts/check-web-image.sh` → all five OK, exit 0; no container or image left behind.
- `scripts/tests/check-web-image.test.sh` → 13 passed. `scripts/check-compose-exposure.sh` → all OK.
- The image build runs `npm ci` and `npm run build` (Next production build) successfully.

## Risks / notes
- CI (AOS-622) should run `scripts/tests/check-web-image.test.sh` and, where Docker is available,
  `scripts/check-web-image.sh`.
