## Description
- **Compose:** an `ollama` profile, opt-in, that runs a local model server for the AI layer's Ollama adapter (AOS-702).
- **Bake-off:** a documented command that runs local models through the categorisation golden set via the AI port and prints a comparison against the rules and the recorded Claude answers. Passing models can be given an eval record so the start-up gate (D-68) lets them be enabled.
- **Recommendation:** a default small model, with evidence.

## Why
D-67 says features that read raw text should default to a local model, and that local models must be measured on our own golden sets: no public benchmark covers Indian bank text (research §2.3). AOS-702 built the Ollama adapter; this makes it runnable and measurable.

## Scope
- **In:** the compose profile (loopback only), the bake-off command and Gradle task, tests with a local stub (no Ollama needed), a run on real local models, a recommendation, and the guide.
- **Out:** a message-reading golden set (none exists yet; AOS-705 will add one and can reuse this harness); GPU set-up; making a local model the default for categorisation (that is Pragun's call after reading the numbers).

## Acceptance criteria
- [x] `docker compose --profile ollama up -d ollama` starts Ollama; nothing starts it without the profile.
- [x] Security: the port is published only as `127.0.0.1:11434:11434`; a test fails on any bare host port in compose.
- [x] `./gradlew -q aiBakeOff -Pmodels=…` runs each model through the golden set via the AI port and prints rules / rules + Claude (recorded) / rules + each model: accuracy, macro-F1, coverage, rows labelled, valid/rejected/unavailable answers, agreement with Claude, latency, rules kept, gate.
- [x] Gate: a model passes only if it meets the rules baseline (D-61), never changes a rule-decided row, and gives a valid answer to ≥ 90% of questions. `-PwriteEvalRecord` records passing models only.
- [x] Tests need no Ollama: a local stub server plays good, useless and broken models.
- [x] A default small model is recommended, with the numbers.

## Design (see docs/ENGINEERING.md §6)
- **Context:**
  - AOS-702 gives `OllamaProvider`, the gateway, and the eval gate with committed records.
  - The golden set and the recorded Claude answers live in test resources.
  - The only golden set today is categorisation.
- **Where the bake-off runs. Options considered:**
  1. **A JVM command on the test classpath, through the real port (chosen):** it uses the same gateway, redaction, validation and audit as production, so what it measures is what would run. It reads the golden set where it lives, and Gradle runs it like `categorizationReport`.
  2. **A shell script calling Ollama directly** with the prompt copied in: simple, but it skips the redactor and validator and drifts from the real prompt. Rejected.
  3. **A unit test that needs Ollama:** it would break every build without a model server. Rejected; tests use a stub.
- **What counts as passing. Options considered:**
  - (a) **The rules baseline, rules kept, and ≥ 90% valid answers (chosen).** D-61 says a model-assisted variant must beat or match the rules. The valid-answer floor stops a model that rejects everything from "matching the rules" while doing nothing.
  - (b) The rules + Claude floor (`baseline-ai.json`): stricter, but that floor comes from synthetic answers, so a real local model would be held to a made-up bar.
- **Compose exposure options:**
  - (a) no published port: safest, but the bake-off runs on the host and couldn't reach it;
  - (b) **`127.0.0.1:11434:11434` (chosen):** reachable from the host only. Ollama has no authentication, so a bare port is never allowed, and a test enforces this for every service.
- **Decision:** 1 + (a) + (b), D-69. **Patterns:**
  - Strategy (each model is a labeller in the D-61 harness);
  - Adapter (`OllamaProvider`);
  - Specification (the eval gate).
- **Extensibility:**
  - another model is one more name in `-Pmodels`;
  - another feature's golden set (message reading, AOS-705) reuses `BakeOffRun` and the table, with its own labeller;
  - another local runtime (llama.cpp server) is one more `AiProvider`.
- **Impact:**
  - compose (new profile and volume);
  - `build.gradle.kts` (task);
  - test sources (bake-off);
  - `OllamaProvider` gains an optional thread count;
  - one guide.
  - No schema, API or web change.

## Verification

## Risks / notes
- **Local models are over-confident.** qwen3:4b answers 0.95 even when wrong ("A2B Adyar Ananda Bhavan" → Other, "a religious institution"; "Cred Rentpay" → EMI). AOS-512's 0.7 threshold doesn't filter for it, so the protection is the gate (rules kept, rules baseline) and `source: ai` with its reason on every label. A calibration step per model (research §9) is a follow-up if a local model becomes the default.
- **The Claude comparison is against synthetic answers**, so "agrees with Claude" is agreement with AOS-512's hand-written stand-ins, not with the real model.
- **CPU only in Docker on a Mac.** Latency depends heavily on load: with 14 threads on a machine at load average about 540, generation dropped to one token every ~17 s. With 4 threads it ran at about 12 tokens/s. The native Ollama app (Metal) would be much faster.
- **No message-reading golden set exists yet**, so only categorisation was measured. AOS-705 should add one; `BakeOffRun` and the table are reusable.
- `OllamaProvider` gained an optional `numThread` (used by the bake-off; production leaves it to Ollama).
- The `gemma3:4b` pull failed once with a 503 from the registry and succeeded on retry.

## Proposed decision D-69

### D-69 — Local models: an opt-in Ollama profile on loopback, measured by a bake-off through the AI port; qwen3:4b recommended
2026-10-17 · Proposed (Claude, AOS-703; awaiting Pragun) · Type: Architecture / Product · Tasks: AOS-703, AOS-702 · Builds on D-61, D-67, D-68
- **Runtime:**
  - Ollama (`ollama/ollama:0.40.6`) as a compose service under the `ollama` profile, so nothing starts it by default;
  - models in the `ollama_models` volume;
  - published only on `127.0.0.1:11434` (Ollama has no authentication), with `ComposeExposureTest` failing on any bare host port in compose;
  - the API reaches it at `http://ollama:11434`.
- **Measurement:**
  - `./gradlew -q aiBakeOff -Pmodels=…` runs each model through the golden set **via the AI port** (same prompt, redaction, validation and audit as production);
  - it prints rules / rules + recorded Claude / rules + each model: accuracy, macro-F1, coverage, AI labels, valid/rejected/unavailable answers, agreement with Claude, latency, rule rows kept and gate.
- **Gate for a local model:**
  - the rules baseline (D-61: match or beat the rules);
  - no rule-decided row changed;
  - at least 90% schema-valid answers (so a model that rejects everything can't pass by "matching the rules").
  - `-PwriteEvalRecord` records passing models only (`answers: live`). Their answers are committed and replayed by a test, so records can't drift.
- **Recommended default local model: `qwen3:4b`.** On the golden set it scored 89.9% accuracy and 0.894 macro-F1 (rules 82.6% / 0.827; recorded Claude 91.7% / 0.913), with all answers valid, all rule rows kept and about 2–3 s per question on a busy CPU.
  - `gemma3:4b` (89.2%) is the alternative.
  - Models under 4B parameters failed a category floor.
- **Not changed:** categorisation still defaults to Claude Haiku when enabled. Switching to local is `AI_CATEGORIZATION_PROVIDER=ollama`, `AI_CATEGORIZATION_MODEL=qwen3:4b` (Pragun's call).
- **Rejected:**
  - a shell script calling Ollama directly (skips redaction and validation, drifts from the real prompt);
  - tests that need Ollama (they would break every build; a stub server is used instead);
  - holding local models to the rules + Claude floor (that floor comes from synthetic answers);
  - no published port (the host-side bake-off couldn't reach it).
- **Consequence:**
  - any feature with a golden set can be measured on local models with the same harness;
  - a model change is a bake-off, a committed record and a config change.
