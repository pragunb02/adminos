## Description
The statement parser (`services/pdf-parser`) capped only the upload size (20 MB). It had no limit on time, pages or
rows (AUD-22, [AUDIT-2026-10](../security/AUDIT-2026-10.md)). The parse also ran synchronously on the event loop,
so one slow file blocked every other request.

## Why
Availability: a crafted PDF or spreadsheet could pin the parser's CPU or memory for as long as it liked. The API
gives up after 60 s, but the parser kept working. Low, CVSS 2.7 (owner-only upload; T3 stolen session, or a
hostile file the owner is tricked into uploading).

## Scope
- **In:**
  - a per-file wall-clock limit that really stops the work;
  - page, sheet, row and cell caps for every format;
  - a memory ceiling for the parse;
  - running the parse off the event loop;
  - hostile-file tests.
- **Out:** the API side (it already caps 20 MB and waits 60 s, and relays the parser's 422 code and message unchanged); the container hardening of AOS-622.

## Acceptance criteria
- [x] A parse that runs longer than 30 s is killed and answers 422 `PARSE_TIMEOUT`. Tests: `test_a_parse_that_runs_too_long_is_killed`, `test_the_real_endpoint_answers_parse_timeout_when_the_limit_passes`
- [x] A PDF with more than 300 pages answers 422 `TOO_MANY_PAGES`. Tests: `test_a_pdf_with_too_many_pages_is_refused_with_the_real_cap`, `test_a_pdf_at_the_page_cap_is_read`
- [x] More than 100 000 rows or 2 000 000 cells, across all tables and sheets, answers 422 `TOO_MANY_ROWS`. An `.xls` file is refused from its declared size, before it is read. ## Design
- **Context:** `parse(...)` was an `async` endpoint that called the synchronous `parse_statement` directly. The readers
  materialised every row of every table, sheet and page.
- **Options considered:**
  1. Run the parse in a thread with `asyncio.wait_for`. Python can't stop a thread, so the work goes on after the timeout.
  2. Use `signal.alarm` / `SIGALRM`. It only works on the main thread, and pdfminer's C-level loops don't see it.
  3. **One short-lived child process per parse (`spawn`), killed on timeout, with `RLIMIT_AS`** (chosen). Each parse costs about 0.1–0.3 s to start, which is acceptable for a single-user service.
  4. A process pool. A worker that hangs or bloats stays in the pool, and killing it means rebuilding the pool.
- **Decision:**
  - **`app.isolation.run_isolated(target, args, timeout, memory_bytes)`:**
    - starts the child with `spawn`, never `fork`, because the server is threaded;
    - the answer comes back over a one-way pipe, as plain values or a code;
    - when the time is up, the child is killed;
    - when the child dies without answering, that is `ParseCrashed`;
    - any other exception comes back as its type name only.
  - **The endpoint:**
    - waits in the thread pool, so the event loop stays free;
    - runs at most 2 parses at once.
  - **`app.limits.Budget`:**
    - every reader charges each row (and its cells) to it;
    - an `.xls` sheet is checked against its declared size first;
    - pages and sheets are checked against their counts.
- **Patterns:** a parameter object (`Budget`) and process isolation (bulkhead).
- **Impact:** parser only. There are three new error codes, which the web shows through the API's relayed message. No API or contract change.

## Security (threat review, ENGINEERING §4a)
- **Exposes:** nothing new. There is no new route, listener or dependency. The child process has no network listener and inherits no extra privilege.
- **Abuse and what stops it:**
  - **a PDF with thousands of pages, or a deep page tree:** the page cap, plus the time limit for the page-tree walk itself;
  - **pathological content streams or tables that make pdfminer spin:** the 30 s kill;
  - **a sheet that claims a million rows or 16 384 columns:** the row and cell caps (`.xls` from its declared size; `.xlsx` and CSV while reading);
  - **many sheets:** the sheet cap;
  - **a decompression bomb inside an `.xlsx` (zip), or huge shared-string tables:** the 1 GiB address-space limit (MemoryError) and the time limit;
  - **many parallel uploads:** at most 2 children at once; the others wait, and the API times out at 60 s;
  - **an error message that quotes content:** only codes and type names cross the process boundary, and only codes are logged (D-37).
- **Fail closed:** a timeout, a crash, a memory error or any unexpected exception is a 422 with a fixed message. Nothing partial is returned.
- **Tests that attack it:** the unit and endpoint tests above. There is no new screen, so no Playwright spec.
