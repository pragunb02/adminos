## Description
A "Where it leaks" page shows, for each habit lens (AOS-901) and each merchant in it: what was spent, how many orders, the average order, how many orders were late at night, the weekday pattern, and the change from the period before. It works for a week, a month or any custom range, kept in the URL like the console. Every number opens the transactions behind it in Activity. Refunds net off.

## Why
D-80 / BRD §5.6: the owner overspends on quick commerce, food delivery, nights out and online shopping, mostly by UPI, and rarely opens the app. Seeing the leak, with its numbers and its transactions, is step one of "spend less".

## Scope
- **In:**
  - `GET /api/v1/coach/leaks?from&to`: per lens and merchant: spent (spend − refunds), orders, average order, late-night orders / orders with a known time / share, spend per weekday, the previous period's spent and the change; plus the total across all lenses (the union, so overlaps count once).
  - `GET /api/v1/coach/leaks/transactions?from&to&lens&merchant&lateNight&weekday&category&nature&q`: the transactions behind any number (same envelope as `/transactions`).
  - Web `/leaks`: period switcher (`?p=&d=`) plus a custom range (`?from=&to=`); one section per lens; per-lens weekday bars with a table alternative; merchant table; "Not a leak" (removes the merchant from the lens, with undo) and "Add a merchant"; "How we got this".
  - Activity understands `lens`, `merchant`, `late` and `weekday` and shows them as removable filters.
  - Linked from Home (a self-contained "Where it leaks" card) and from More / the desktop rail.
- **Out:** limits and their status (AOS-904), goals (AOS-907), hidden fees from order receipts (AOS-903).

## Acceptance criteria
- [x] For a range, each lens shows spent, orders, average order, late-night share, spend and orders per weekday, and the change vs the same number of days before; each merchant in it shows the same.
- [x] A refund in the range reduces its lens and merchant even when its purchase was earlier (the lens can go negative; nothing is clipped, D-46); transfers, reversals, income and person-to-person UPI never appear.
- [x] Days, weekdays and late night are in the user's zone; a statement row (date only) is never counted as late night; DST zones work.
- [x] Week, month and custom ranges come from the URL; bad ranges are 400 (API) and a visible notice (web).
- [x] Every number links to Activity with matching filters, and Activity lists exactly the transactions behind it.
- [x] The page has loading, empty, error-with-retry and data states; "Not a leak" and "Add a merchant" succeed and fail visibly.
- [x] Home and More link to the page.

## Design
- **Context:** the console's analytics (D-45) aggregate in SQL by (day, nature, category, merchant): no time of day, no UPI handle, no lens. Lens membership (AOS-901) needs the whole transaction (merchant, subcategory, UPI handle, the owner's overrides).
- **Options considered:**
  1. **Extend the analytics SQL** with hour and handle columns and match lenses on aggregated facts: fast for big data, but lens rules (keywords, P2P, overrides) would have to be re-implemented in SQL or fed per row anyway.
  2. **Read the range's transactions and compute in Kotlin** with the AOS-901 matcher (chosen): one definition of lens membership for the page, the drill-down, limits and digests; a single user's months are a few thousand rows. The range is capped like analytics (3 × 366 days).
  3. **A materialised `lens_spend` table** updated by a listener: fastest reads, but a second source of truth to keep in step with re-categorisation, overrides and refunds.
- **Decision:** option 2. **Patterns:** a pure calculator (`LeakCalculator`) over immutable facts; the service only gathers (transactions, overrides, zone) and the routes map DTOs. The drill-down uses the same `LeakFilter`, so a number and its list can't disagree.
- **Definitions** (shown under "How we got this"):
  - spent = spend − refunds, per lens and merchant, in the range (D-46);
  - orders = spend transactions; average order = their total before refunds ÷ orders (an order's size, not reduced by later refunds);
  - late night = an order between 22:00 and 05:00 local time (from `lenses.json`); share = late-night orders ÷ orders with a known time. Statement imports carry no time, so they are left out of the share;
  - previous period = the same number of days immediately before (D-46); change = % of the previous spent (none if that was 0 or less);
  - total = all lenses together, each transaction once.
- **Extensibility:** a new lens is one JSON entry; a new per-lens number is one field in `LensLeak` and the calculator.
- **Impact:** `domain/coach/leaks/*`, coach route module, web `/leaks`, `lib/leaks.ts`, Activity filters, a Home card, Nav. No schema change.

## Security (D-100, docs/ENGINEERING.md §4a)
- **Exposes:** two authenticated read routes (`/api/v1/coach/leaks`, `/api/v1/coach/leaks/transactions`), one new page (`/leaks`), new Activity URL filters. Reads the owner's own transactions; writes nothing new (lens edits use the AOS-901 routes).
- **Abuse and what stops it:**
  - *Signed out / forged token:* both routes are inside `authenticate("auth-jwt")` → 401 (route tests); the page is behind the web route guard → `/login` (Playwright).
  - *Another user's data:* every read is scoped to the token's user id; another user sees zeros and an empty list (route test).
  - *Hostile parameters:* `lens` must be a shipped lens id or `all`; `weekday`, `nature` (spend/refund only), `category`, `lateNight`, `limit` (1..1000), `merchant` and `q` (≤255) are validated → 400 naming the parameter. Search text is a plain substring filter in Kotlin, never SQL (injection strings, `%`, `_` tested). Ranges are capped at 3 × 366 days (no unbounded reads).
  - *Untrusted text in the UI:* merchant names come from bank narrations; React renders them as text (unit test and Playwright check that `<img onerror>` does not render or run). URL values are re-validated on the web side (bad lens ids ignored, bad dates fall back with a notice).
  - *CSRF:* GET only here; mutations reuse the AOS-901 routes (SameSite=Strict cookie).
- **Data / secrets / listeners / dependencies:** nothing stored, nothing logged, no new listener, no new dependency.

## Proposed decision D-82 — Leaks are computed from transactions with the lens matcher; every number has its drill-down
2026-10-18 · Proposed (background agent) · Type: Architecture / Product · Tasks: AOS-902 · Builds on D-39, D-45, D-46, D-49, D-81
- **Where:** the leaks read the range's spend and refunds and match lenses in Kotlin (AOS-901 matcher with overrides), not in SQL; range capped at 3 × 366 days. Limits, digest, report card and goals reuse `LeakService.facts`, so every coach number agrees.
- **Definitions:** spent = spend − refunds, not clipped (a lens can be negative); orders = spend transactions; average order = orders' total before refunds ÷ orders; late night = 22:00–05:00 local (data file), share over orders with a known time (statement rows excluded); previous = same number of days before; total across lenses = union.
- **Drill-down:** `/api/v1/coach/leaks/transactions` uses the same filter object as the numbers; Activity shows it via `lens`, `merchant`, `late`, `weekday` URL filters.
- **Rejected:** analytics SQL with hour/handle columns (would duplicate lens rules in SQL); a materialised lens-spend table (a second source of truth to keep in step with corrections and overrides).
