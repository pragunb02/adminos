## Description
- One API that defines every number on the console, in the user's timezone.
- `GET /api/v1/analytics/summary`, `/series`, `/categories` and `/merchants`; `from`/`to` are dates, defaulting to this month so far.

## Why
- Today there is only `/transactions/summary`, which returns category totals as inexact numbers, with no comparison and no time series.
- Every console view (AOS-303…306) needs the same definitions.

## Acceptance criteria
- [x] **spent** = spend − refunds; **received** = income; transfers and reversals are excluded (D-39).
- [x] Total = Σ categories = Σ series buckets, for the same period (D-46).
- [x] The summary includes the previous period of the same length, plus the change.
- [x] The series: day/week (Monday)/month buckets in the user's timezone, zero-filled.
- [x] Categories: spent, share, count and previous spent, largest first. Merchants: top N by spent, with count.
- [x] Amounts are exact decimal strings (D-30); bad ranges or buckets give a 400 naming the parameter.
- [x] The same answers from Postgres and in-memory.

## Design (plan approved, D-45)
- **One aggregation query** returns facts grouped by (local day, nature, category, merchant): sum and count.
  - The local day is `(transacted_at AT TIME ZONE tz)::date`.
- **`AnalyticsService`** computes summary, series, categories and merchants from the facts: one place for the rules, easy to test.
  - Postgres does the heavy grouping; at one user's scale the facts are small (tens to a few thousand rows).
  - If public scale needs more, specialised queries can replace a method without changing the API.
- **Limits:** at most 3 years per request, and at most 400 buckets.
