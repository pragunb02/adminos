## Description
- The Go Gmail handler was the last writer that bypassed the pipeline: it inserted every email transaction as `debit`, with a possibly blank payment method.
- Now it writes a normalized `ingest_events` row (source `gmail`, keyed by the Gmail message ID) with a detected direction.
- The Kotlin pipeline then handles duplicates, transfers, refunds and categories, like every other source.

## Why
- **Wrong totals:** salary or refund emails counted as spending.
- **Gmail skipped the accuracy engine,** so the same payment from SMS and email was counted twice.
- **A silent fallback:** with no token, or a failed fetch, the job used an empty email list and reported the sync as successful.

## Scope
- **In:**
  - direction detection (D-43);
  - the ingest-event write, idempotent by message ID;
  - the job fails when Gmail can't be reached;
  - removing the unused Go categorizer;
  - Go unit tests.
- **Out (AOS-401):** full email body parsing (snippet only today), incremental history sync, Pub/Sub watch. Bills unchanged.

## Acceptance criteria
- [x] "debited from your a/c" → debit; "credited to your a/c" / "received" / "refund" → credit, even when the email also mentions the other side.
- [x] An unclear direction is skipped and counted as needs-review, never guessed.
- [x] Gmail transactions become `ingest_events` rows (pending), never direct `transactions` rows; re-syncing the same email is a duplicate.
- [x] An unknown payment method is NULL, never blank.
- [x] No token, or a fetch error → the job fails (no "success" with zero emails).
- [x] The Go build, vet and tests pass.

## Design (approved by Pragun 2026-10-16, "ok")
- `detectDirection(text)`:
  1. A phrase anchored to your account wins: `debited from / credited to (your) a/c|account|card`.
  2. Otherwise, exactly one family of words present → that direction.
  3. Otherwise → unclear.
- `occurredAt` is the email's Date header (the precise time); otherwise the date in the body (00:00 IST).
- The API processor's sweep (5 s) picks the events up.
