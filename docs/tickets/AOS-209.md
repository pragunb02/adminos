## Problem
- A refund showed up as income, so the month looked better than it was, and the category it came back to still showed the full spend.
- A failed payment that the bank reversed counted as spending, plus income of the same amount.

## Design (approved by Pragun, D-39 / D-40)
- **Reversal:** both sides become `reversal` and net to zero.
- **Refund:** the credit becomes `refund`, takes the original's category, and **reduces that category's spending** (spend − refunds per category; a category that nets to ≤0 drops out).
- Same links, bands and review API as AOS-207/208. A category the user set is kept.

## Rules (`RefundReversalDetector`, D-40)
- **Reversal:** exact amount, same or unknown account, credit 0–5 days after the debit.
  - **Score:** base 4; same payment reference +6; reversal narration (`REV`, `REVERSAL`, `REVERSED`, `FAILED`…) +4; same day +2 / next day +1.
  - **Bands:** ≥8 auto, 6–7 suggest. A refund narration without a reversal one is never a reversal.
- **Refund:** credit ≤ debit, and refunds so far + this credit ≤ debit; same or unknown account; 0–90 days.
  - **Merchant link required:** VPA or the same merchant tokens = 3, overlapping tokens 1–2.
  - **Score:** + refund narration 4, full amount 2, same account 1. **Bands:** ≥8 auto, 5–7 suggest.
- **Ambiguity margin 3:** two close candidates → suggest only.
- **Works in either order:** a statement may bring the refund before its purchase.

## Implementation
- `TransactionRepository.findInWindow(type, from, to, minAmount, maxAmount)` (Exposed + in-memory).
- `RefundReversalStep`, last in the pipeline; it uses the generic `Relation` side effects from AOS-208.
- `applyRelation` is shared by the step and `SuggestionService.confirm`.
- `spendingByCategory` = spend − refunds (`netOfRefunds`), in both implementations.
