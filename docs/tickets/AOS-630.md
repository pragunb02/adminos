## Description
Every verified Gmail push queued a new incremental sync (AUD-27, [AUDIT-2026-10](../security/AUDIT-2026-10.md)).

A Pub/Sub push token stays valid for about an hour, and the push body isn't bound to it. So a captured token can be
replayed, with any body, as often as the sender likes. Each replay costs a queued job, a sync session row and Gmail
API quota. Syncs are idempotent, so no data is wrong, but replays could multiply without bound.

## Why
Availability and quota (T5 network observer, or a leaked token). Low, CVSS 2.2. The audit's accepted risk (a token
valid for its lifetime) relies on this task to bound the effect.

## Scope
- **In:**
  - API: a `GmailPushService` (domain) decides what a push does: `NoConnection`, `NotActive`, `AlreadySynced`, `Coalesced` or `Queued`.
  - The route maps each outcome to a 200 ack.
  - `SyncSessionRepository.findQueued`.
  - Worker: marks its session `in_progress` when it starts.
- **Out:**
  - Pub/Sub token lifetime (Google's design);
  - Asynq-level uniqueness;
  - the daily fallback and the manual sync (unchanged).

## Acceptance criteria
- [x] While a sync of the connection is queued and not started, more pushes (replays included, with any history ID) queue nothing and are acknowledged with 200 and the pending session's ID. Tests: `a hundred replays …`, `a replay with a forged larger history ID …`, route `replaying a captured push while its sync is queued …`
- [x] Concurrent pushes queue exactly one sync. Test: `concurrent pushes queue exactly one sync`
- [x] A push that arrives while a sync is **running** queues the next one, and only one waits. Mail that arrives during a sync is never left for the daily fallback. Test: `a push during a running sync queues the next one …`. Worker: `TestASyncMarksItsSessionStartedBeforeReadingGmail`
- [x] A push at or before the stored history ID queues nothing ("Already synced"). A non-numeric stored ID never suppresses a push. Tests: the service tests, plus route `a push for a change the last sync already read …`
- [x] A queued session older than 10 minutes counts as lost and no longer absorbs pushes. Test: `a queued sync older than the window is treated as lost`
- [x] Postgres lookup: the newest queued session after the cutoff, for that connection only. Test: `IngestionRepositoriesIntegrationTest` › `the queued session lookup …`
- [x] The worker's mark is best effort: when it fails, the sync still runs. Tests: `TestASyncStillRunsWhenItCantMarkItsSessionStarted`, and the Postgres `TestGmailStoreMarksSessionsStarted_Integration` (tagged `integration`)

## Design
- **Context:** the worker never set `in_progress`, so a session stayed `queued` until it completed. Without that state, "a sync is queued" would also cover "a sync is running", and coalescing would drop pushes for mail that arrived mid-sync.
- **Options considered:**
  1. **A time window** (at most one push sync per N seconds). Simple, but a push inside the window after a sync has already listed history loses that mail until the next push or the 06:00 fallback.
  2. **Asynq unique tasks.** These live in the worker's queue and are invisible to the API's session records, and they have the same running-versus-waiting problem.
  3. **Coalesce into a queued, not-yet-started session, plus the stored-history check** (chosen). The worker marks `in_progress` at start (the column and enum value already exist). It is exact: a waiting sync reads up to the mailbox's position when it runs, so nothing is lost.
- **Decision:**
  - `GmailPushService.onPush(email, historyId)`:
    - drops the push when `historyId ≤ stored`;
    - under a `Mutex`, returns `Coalesced` if `findQueued(connection, now − 10 min)` finds a session;
    - otherwise it enqueues as before.
  - The route keeps its signature (the service is created by default), and every outcome is a 200, so Pub/Sub doesn't retry.
- **Patterns:** a domain service with a sealed outcome; the route only maps it (moves the logic out of the route, per ENGINEERING §1).
- **Impact:**
  - **API:** domain, repository, route. No schema change.
  - **Worker:** one `UPDATE` at start.
  - **Contracts:** none.
  - **Rate:** at most one running and one waiting sync per connection.

## Security (threat review, ENGINEERING §4a)
- **Exposes:** nothing new. The route is the same: unauthenticated by design (allowlisted in the route inventory), and gated by the Google OIDC check.
- **Abuse and what stops it:**
  - **A replayed token with the same body:** `AlreadySynced` once a sync has stored the history ID; `Coalesced` before that.
  - **A replayed token with forged bodies** (rising history IDs, other addresses):
    - unknown addresses queue nothing;
    - for the owner's address, at most one sync waits at a time;
    - forged IDs can't skip a real change, because a skip happens only when the ID is at or below what a sync already stored.
  - **A flood of parallel replays:** the lock lets exactly one through.
  - **A dropped job** (Redis flush) leaving a session `queued` forever: it stops coalescing after 10 minutes.
- **Fail closed / no loss:**
  - If the worker can't mark the session started, a push during that sync is folded into it. That mail waits for the next push or the fallback, which is bounded and logged.
  - Every outcome is acknowledged, so a refusal never makes Pub/Sub retry (retries would only add pushes).
- **Tests that attack it:**
  - unit: replays, forged IDs, concurrency, stale sessions;
  - route: replay over HTTP;
  - integration: the Postgres lookup and the worker mark.
  - No screen, so no Playwright spec.
