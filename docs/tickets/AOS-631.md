## Description
`NotificationsReminderEngineCoverageTest` built its bills from `LocalDate.now()` (the JVM's default zone)
while `ReminderEngine` judges each bill on the user's date through `UserCalendar` (India time for a user
with no zone). With a UTC JVM (CI, the container) the two dates differ every day from 18:30 to 24:00 UTC,
and two tests failed in that window:
- `runReminders marks overdue bills and sends due reminders`
- `runReminders keeps going when one bill fails`

## Why
ENGINEERING §3: tests are deterministic and inject `Clock`. A test that fails for 5.5 hours a day would make
the `api` CI check (AOS-622) red at random once it is required.

## Scope
- **In:** the reminder engine coverage test and every other unit or integration test that fails when the
  JVM zone and the India date disagree; `BillTrackingServiceTest` (same pattern, wall-clock bill dates).
- **Out:** production code (no behaviour change). Remaining `LocalDate.now()` uses in tests that compare
  against code reading the same JVM clock are listed under Risks, not changed.

## Acceptance criteria
- [x] The reminder engine test reads one fixed clock (18:45 UTC on 16 Oct, India already on the 17th) for
  the bill repository, the calendar and its own dates. → `NotificationsReminderEngineCoverageTest`
- [x] Regression tests just before and just after India's midnight (18:29 and 18:31 UTC): overdue marking
  and the 3-day reminder follow the India date while UTC is still on the 16th. → 4 new tests
- [x] `BillTrackingServiceTest` reads a fixed clock for due dates and payment times.
- [x] Proven independent of the JVM zone: the full unit suite and the two fixed classes pass with the JVM
  default zone set to UTC, `Pacific/Kiritimati` (UTC+14), `Pacific/Pago_Pago` (UTC−11) and `Asia/Kolkata`.

## Design
- **Context:** `UserCalendar(users, clock)` and `InMemoryBillRepository(clock)` already accept a clock.
  `TestClock.withZone` returns itself (always UTC), so it can't stand in for a zoned calendar clock; the
  tests use `Clock.fixed(…, UTC)`, whose `withZone` is honoured.
- **Options considered:** 1) fixed clock injected into the engine's collaborators; 2) set
  `-Duser.timezone=Asia/Kolkata` for the test JVM (hides the bug, and the container runs UTC).
- **Decision:** option 1. **Patterns:** dependency injection of time.
- **Impact:** tests only.

## Security (threat review, ENGINEERING §4a)
- **Exposes:** nothing. Test-only change: no route, input, data, secret, dependency or listener.
- **Abuse:** none possible. The fix removes a flaky check that could have trained people to ignore a red
  `api` gate (a process risk for D-100).
- **Checks:** no secrets or personal data in fixtures (bill names are generic billers, amounts synthetic).

## Verification
- Before the fix, at 20:13 UTC: `JAVA_TOOL_OPTIONS=-Duser.timezone=UTC ./gradlew test` → the two tests
  above FAILED; same with `Pacific/Pago_Pago`; `Pacific/Kiritimati` and the Mac's own zone passed.
- Integration tests with `UTC` and `Pacific/Kiritimati`: all pass before and after (no zone mismatch).
- After: unit suite with `UTC`, `Pacific/Kiritimati`, `Pacific/Pago_Pago`, `Asia/Kolkata` → green;
  `./gradlew test integrationTest koverVerify` → green.

## Risks / notes
- Other tests still call `LocalDate.now()` but compare with code that reads the same JVM clock (the
  in-memory or Exposed bill repository), so they don't flake; they are not deterministic either. A
  follow-up could forbid zone-less `now()` in tests through `TestConventionsTest`.
- Production finding (not changed here): `ExposedBillRepository.findUpcoming/findOverdue` use
  `LocalDate.now()` (JVM zone, no injected clock); the engine's one-day slack covers a UTC server.
  `InMemoryBillRepository` and `dashboardRoutes` default to `Clock.systemDefaultZone()`.
- `TestClock.withZone` ignores the zone; a test passing it to `UserCalendar` would get UTC dates.
