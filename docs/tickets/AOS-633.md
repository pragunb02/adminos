## Description
A body that isn't JSON (a form, plain text, or none) on any route that reads JSON, e.g.
`POST /api/v1/transactions/cash`, answered **500**. Ktor throws `CannotTransformContentToTypeException` /
`UnsupportedMediaTypeException`, both `ContentTransformationException`s, which extend `IOException`, so
they fell into the I/O branch of `ErrorHandling.kt` and became a 500. Malformed JSON was already a 400, but
its message carried the decoder's text, which quotes the input ("but had '1' instead") and parser offsets
(audit finding AUD-15).

## Why
A 500 for a client's mistake hides real server errors in the logs and alerts, and a reflected decoder
message leaks input and internals (AUD-15, D-91).

## Scope
- **In:** mapping Ktor's body errors in `infrastructure/plugins/ErrorHandling.kt`; route tests on the real
  `Application.module`; plugin tests.
- **Out:** the other AUD-15 messages (VALIDATION_001–003 and `No enum constant…` from routes) are AOS-618's
  (PR #107).

## Acceptance criteria
- [x] A form, plain-text, odd-type or missing body on a JSON route is **415** `VALIDATION_005`
  "Unsupported request body type". → `RequestBodyErrorsRoutesTest`
- [x] Malformed JSON, an empty JSON body and JSON of the wrong shape are **400** `VALIDATION_004`
  "Malformed request body". → `RequestBodyErrorsRoutesTest`
- [x] No answer echoes the input or names internals: a canary with markup, the bad token, class and
  package names, `Exception`, parser offsets and `JSON input` are all absent; every answer is the standard
  envelope with a request id. → `RequestBodyErrorsRoutesTest` (every case, every route)
- [x] Representative routes, signed in as other route tests are: cash entry, notification preferences
  (PATCH), push subscription, ingest events; and the public sign-in route (owner email configured, AOS-614).
- [x] Without a session, a form body on a protected route is still 401 (auth runs before the body is read).
- [x] A JSON-typed body Ktor can't transform is 400; a non-JSON one 415; an unparseable Content-Type 415;
  Ktor's `PayloadTooLargeException` is 413 `VALIDATION_006`. → `InfraPluginsCoverageTest`
- [x] A valid JSON body still works.

## Design
- **Context:** StatusPages picks the most specific registered exception type, so handlers for Ktor's
  `ContentTransformationException` family take precedence over the `IOException` one.
- **Options considered:**
  1) 415 vs 400 by exception type only: Ktor throws `CannotTransformContentToTypeException` (not
     `UnsupportedMediaTypeException`) for a form or text body, so this would make them 400.
  2) **415 when the request's Content-Type isn't JSON (`application/json` or `+json`), else 400.**
  3) Keep the decoder's message but filter it (AOS-618's `publicMessage`): the first line still quotes the
     offending character and offsets; a filter is a denylist.
- **Decision:** 2, with fixed messages (proposed D-102). **Patterns:** fail closed; allowlist of what a
  client sees (only fixed strings).
- **Impact:** API error mapping only; `VALIDATION_004` keeps its code with a fixed message; new codes
  `VALIDATION_005` (415) and `VALIDATION_006` (413). The web app doesn't read these messages.

## Proposed decision
**D-102 (Architecture, AOS-633):** request bodies the API can't read get fixed answers: 415
`VALIDATION_005` when the request's Content-Type isn't JSON (including none or an unparseable one), 400
`VALIDATION_004` "Malformed request body" for JSON that doesn't parse or fit, 413 `VALIDATION_006` for
Ktor's body limit. No decoder or library text reaches the client (supersedes the decoder-text suffix of
`VALIDATION_004`; the field-naming messages from our own `require(...)` checks are unchanged).

## Security (threat review, ENGINEERING §4a)
- **Exposes:** nothing new; fewer details in error answers.
- **Abuse and what stops it:**
  - a stranger probing with odd bodies → can't reach the API (tailnet only, D-91); if they could, the
    protected routes still answer 401 before reading the body (tested), and the sign-in route answers a
    fixed 415/400;
  - reflected input (XSS in a client that renders errors, or log/response confusion) → fixed strings only;
    the Content-Type sent is never echoed (tested with markup in it);
  - noisy 500s masking real faults or tripping alerts → client errors are 4xx and are not logged as errors.
- **Tests that attack it:** hostile bodies (markup canary, broken JSON, wrong shapes, odd and unparseable
  content types) on five real routes; auth-before-body check.
- **Checks:** no new dependency, listener or stored data; no secrets; fixtures use `owner@example.com`.
