## Description
The secure holdings store for Epic E8, wave 1 "my mutual funds, safely":
- the wealth domain model: investment accounts → instruments → an **append-only** ledger of typed transactions, and import batches that can be undone;
- exact number types `Quantity`, `UnitPrice`, `FxRate` (and `CurrencyAmount`), never `Double`;
- account identifiers (folio, BO ID, account numbers, UAN, PRAN) **encrypted in the app** with AAD under a key reserved for wealth, looked up by a keyed **blind index**, shown as the last 4 only;
- a wealth audit trail that can carry only codes and counts.

## Why
D-79: wealth data is the most sensitive data in the app (threat model A6), and every later E8 task (CAS import, prices, lots, XIRR, the holdings screen) needs one model with exact numbers. AOS-803 (backups) is already covered by AOS-621 / D-98, which D-79 requires before real holdings are stored.

## Scope
- **In:** `domain/wealth` (`Numbers.kt`, `Model.kt`, `Repositories.kt`, `WealthAudit.kt`), `infrastructure/crypto/WealthIdentifiers.kt` (HKDF + blind index), `V70__wealth_store.sql`, Exposed tables and repositories, Koin wiring (`di/WealthKoinModule.kt`), tests.
- **Out:** importing (AOS-805), prices (AOS-810), lots and returns (AOS-811/812), routes and UI (AOS-805/820), identifier reveal with re-auth and privacy mode (AOS-804), lots/snapshot tables (later tasks).

## Acceptance criteria
- [x] Accounts, instruments, append-only investment transactions and import batches exist in Postgres (V70) with InMemory and Exposed repositories that pass one shared contract (`WealthStoreContract`).
- [x] `Quantity` (18 places), `UnitPrice` (positive, 10 places) and `FxRate` (positive, 10 places, rate type and date) refuse anything finer than their column instead of rounding; wire decimals refuse exponents, grouping and words (`NumbersTest`).
- [x] Identifiers are AES-256-GCM (TokenEncryptor v2) with row-bound AAD under an HKDF-derived wealth key, indexed by HMAC-SHA-256 under a second derived key, and only the last 4 are stored in clear (`WealthIdentifiersTest`, integration test reads the raw row).
- [x] The wealth key is not the token key: a wealth ciphertext doesn't decrypt with `TOKEN_ENCRYPTION_KEY` directly (test).
- [x] Ledger rows can't be updated in place: the database refuses (trigger, integration test). Corrections are new rows (`supersedes_id`).
- [x] Recording the same rows twice (or four imports at once) adds each row once; an undone batch hides its rows and the same file can be imported again (contract + concurrency test).
- [x] Audit rows for wealth carry only counts and short codes; free text is refused (`WealthAuditTest`).

## Design
- **Context:** `TokenEncryptor` v2 (D-59) encrypts Gmail tokens with `TOKEN_ENCRYPTION_KEY`; the vault wraps per-file keys with it (D-60). There was no investment model. Backups exist (D-98).
- **Options considered:**
  1. **Key:** (a) reuse `TOKEN_ENCRYPTION_KEY` as is; (b) a new `WEALTH_ENCRYPTION_KEY` secret; (c) **HKDF-SHA-256 purpose keys derived from `TOKEN_ENCRYPTION_KEY`** (`adminos/wealth/v1/encrypt`, `adminos/wealth/v1/index`). (a) mixes purposes, so rotating one rotates all; (b) adds a second secret to escrow and lose (D-60's consequence twice). (c) keeps one escrowed secret and still separates purposes: chosen (research §6.3, D-79).
  2. **Lookup:** (a) a plain SHA-256 of the identifier: brute-forceable, a folio is 8–11 digits; (b) **HMAC under a derived key**: equality only, useless without the key. Chosen (b).
  3. **Append-only:** (a) by convention in the repository; (b) **plus a database trigger** that refuses `UPDATE`. Chosen (b): the guarantee holds even for a buggy future repository or a hand-run query.
  4. **Idempotent re-import vs undo:** (a) a unique `(user_id, source_ref)`: an undone batch would block re-importing the file; (b) **unique within a batch, and "already in an applied batch" checked under a per-user lock** (`SELECT … FOR UPDATE` on the user row, READ COMMITTED). Chosen (b).
- **Decision:** proposed **D-128** below. **Patterns:** Repository (InMemory + Exposed on one contract), value objects for numbers, append-only ledger.
- **Extensibility:** a new asset type is an `InvestmentAccountKind` / `InvestmentTxnType` value (+ the SQL check list); a new identifier is an `IdentifierKind`; key rotation is a `v2` info string plus a re-encrypt job.
- **Impact:** new tables only; `buildAppModule` gains one `includes(...)` line. No route yet, so no route inventory change.

## Security (D-100, docs/ENGINEERING.md §4a)
- **Exposes:** no routes, uploads, jobs or outbound calls. New stored data: investment accounts (encrypted identifier, blind index, last 4, institution name), instruments (public reference data), ledger rows (quantities, prices, amounts), import batches (counts).
- **Abuse and what stops it:**
  - *Database copy or backup leak (T5/T6, A6):* identifiers are ciphertext under a key that isn't in the database or the backup (D-98 keeps `TOKEN_ENCRYPTION_KEY` out of the bucket); the blind index is an HMAC, so folio numbers can't be guessed from it; only the last 4 are clear (integration test reads the raw row).
  - *Ciphertext moved between rows:* AAD `investment_accounts:<id>:identifier`; another row's context fails (test).
  - *Purpose confusion:* the wealth key is derived (HKDF) and differs from the token key (test).
  - *Hostile identifiers (T4 via a crafted statement):* only `[A-Z0-9/-]{1,40}` after removing whitespace; control characters, bidi overrides, other scripts, SQL and HTML are refused before anything is stored (test).
  - *History rewritten:* the trigger refuses updates to ledger rows (test); undo only flips a batch status.
  - *Duplicate rows from concurrent imports:* per-user row lock at READ COMMITTED; four concurrent imports of the same five rows add five (test).
  - *Impossible values from a parser bug:* types refuse negative amounts, zero prices, units moving the wrong way, scale overflow (tests); the SQL checks repeat the key ones.
  - *Audit leakage:* `WealthAudit` accepts only integer counts and `[a-z0-9_.-]{1,40}` codes (test).
- **Not encrypted (justified, D-79):** ISIN, AMFI code, quantities, amounts: needed for aggregation; protected by full-disk encryption, the private network (D-97) and encrypted backups (D-98).
- **Secrets:** none new; tests derive keys from a public seed at run time.
- **Dependencies:** none (HKDF from the JDK's HMAC).

## Proposed decision D-128 (for the integrator)
### D-128 — Wealth identifiers: HKDF purpose keys from the token key, HMAC blind index, append-only ledger enforced by the database
2026-10-18 · Proposed · Type: Architecture · Tasks: AOS-802 · Builds on D-59, D-60, D-79, D-98
- **Keys:** two keys derived with HKDF-SHA-256 (RFC 5869) from `TOKEN_ENCRYPTION_KEY`, salt `adminos-wealth-keys`, info `adminos/wealth/v1/encrypt` and `adminos/wealth/v1/index`. One secret to escrow; purposes separated; rotation by a new info version and a re-encrypt job.
- **Identifiers** are `TokenEncryptor` v2 ciphertext (AES-256-GCM, random IV) with AAD `<table>:<row id>:<field>`, a blind index HMAC-SHA-256(`KIND:normalised`) for equality lookups, and the last 4 characters in clear for display. Normalised = whitespace removed, upper case, `[A-Z0-9/-]{1,40}` or refused. PAN, names, email, phone and address from statements are not stored at all.
- **Ledger:** rows are never updated (database trigger); corrections are new rows (`supersedes_id`); an import is a batch, undo flips its status and hides its rows; re-import is idempotent by a source ref (a hash over the row's identity using the blind index, never a raw identifier), checked against applied batches under a per-user row lock.
- **Numbers:** `Quantity` NUMERIC(38,18), `UnitPrice` NUMERIC(30,10) > 0, `FxRate` NUMERIC(20,10) > 0 with type and date, money NUMERIC(18,2); the types refuse finer values instead of rounding.
- **Rejected:** a second wealth secret (two keys to escrow and lose); a plain hash as the index (guessable folios); append-only by convention only; a global unique source ref (an undone batch would block re-import).
