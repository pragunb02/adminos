## Problem (found by AOS-312 tests)
- `TokenEncryptor.kt:35` uses only the first 32 bytes of `TOKEN_ENCRYPTION_KEY`, and reads it as UTF-8 text instead of decoding base64, so the key has less than 256 bits of entropy.
- There is no AAD, so an encrypted token can be copied to another row without being detected.
- `docker-compose.yml` and `AppConfig` fall back to **public placeholder values** for `TOKEN_ENCRYPTION_KEY` and `JWT_SECRET`. The repo is public, so an instance started without `.env` has secrets anyone knows.

## Fix
- The key must be base64 that decodes to exactly 32 bytes (`openssl rand -base64 32`).
- Format `v2:` + base64(iv‖ct‖tag), with AAD = a caller-given context (e.g. connection id + field).
- Legacy (unprefixed) values still decrypt with the old derivation, once, so they can be re-encrypted.
- **Secrets:**
  - `docker-compose.yml` uses fail-fast `${VAR:?…}` for `JWT_SECRET`, `TOKEN_ENCRYPTION_KEY` and `DB_PASSWORD`.
  - In database mode the API refuses to start without real secrets.
  - In in-memory dev mode it generates a random per-process secret and logs a warning.

## Regression tests (exist today as `@Disabled("BUG AOS-312 …")`; the fix enables them)
- `CryptoTokenEncryptorCoverageTest` › `keys that differ only after byte 32 are different keys`
- New tests: base64 key required; AAD mismatch fails; legacy value decrypts; DB mode without secrets fails to start.

## Impact
`docker compose up` now needs a `.env` with real secrets (`.env.example` documents how to generate them). Stored Gmail tokens (none exist yet: OAuth isn't set up) would be re-encrypted on read.
