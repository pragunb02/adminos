## Description
PROGRESS item 23 says `infrastructure/plugins/RateLimiting.kt` uses `System.currentTimeMillis()` (no injected clock) and `!!` (ENGINEERING §2). Inject a `Clock`, remove the `!!`, keep the behaviour, and test it, including AOS-618's bounded key map.

**State found on `main`:** AOS-618 had already given `RateLimiter` a `clock` parameter and replaced the `!!`. What was still wrong:
1. The `!!` had become `?: Window(now)`, a silent fallback that **fails open**: if it ever ran, the request would be counted on a window that isn't stored, so it would always be allowed.
2. No factory or route could pass a clock. `RateLimiters.auth()` / `manualSync()` always used the system clock.
3. `LearnedCategoryRoutes.kt` held a **process-wide** `retrainLimiter`, so every application (and every test app) in the JVM shared its counters. That contradicts the file's own "no global state" rule.
4. Constructor inputs weren't validated: tests used `windowSeconds = -1` to fake an expired window.
5. Tests slept (`Thread.sleep(1100)`), against §3's "no sleeps, inject Clock".

## Why
ENGINEERING §2 (no `!!`, no silent fallbacks, `require` at the boundary) and §3 (deterministic tests, injected `Clock`). The limiter guards sign-in (D-94), so failing closed matters.

## Scope
- **In:** `RateLimiter` (fail closed, `require`s); `RateLimiters.auth/manualSync/retrain(clock)`; the retrain limiter per installation; tests on a hand-moved clock, including the bounded key map.
- **Out:** the limits themselves (10/min auth, 5/h manual sync, 6/h retrain: unchanged); the `!!` in `StatementImportService` (the other half of PROGRESS item 23, see Risks); the bugs listed under Risks.

## Acceptance criteria
- [x] All time comes from the injected clock: a clock fixed 25 years in the past still counts a live window.
- [x] No `!!` and no silent fallback: a missing window is an error (fail closed), never a free pass.
- [x] Behaviour kept: the window still counts at exactly its length and starts over 1 ms later; refused requests don't move the window; Retry-After counts down and is never negative; the three endpoint limits keep their numbers.
- [x] Each factory call (and each `learnedCategoryRoutes` installation) is a fresh limiter.
- [x] A limit, window (1 s..1 day) or key bound that isn't positive is refused at construction.
- [x] Bounded key map: no sweep at 1,000 keys or fewer; above 1,000, windows more than two lengths old are swept and windows less than that are kept; under a flood of live keys the oldest go first and the map stays at `maxKeys + 1`; a client newer than the flood keeps its count.
- [x] The plugin lets a client back in once its window has passed, and its Retry-After follows the clock.
- [x] No test sleeps.

## Design
- **Context:** the limiter is a class with a defaulted `Clock` (the codebase's convention: 45 classes take `clock: Clock = Clock.systemUTC()`).
- **Options considered:** 1) a Koin `Clock` bean passed through every route function; 2) clock parameters on the factories, per-installation limiters, and the convention's default at the edge. Option 1 changes six route signatures and their test call sites for no behaviour gain; rejected.
- **Decision:** option 2. `checkNotNull` on `compute`'s result keeps it non-null without `!!`, and fails closed.
- **Impact:** infrastructure plugin + one route default. No contract, schema or config change.

## Implementation plan
1. `RateLimiter`: `init { require(...) }`, `checkNotNull` instead of `?: Window(now)`, named constants `EVICT_ABOVE` and `MAX_WINDOW_SECONDS`.
2. `RateLimiters.auth/manualSync/retrain(clock = system)`; `learnedCategoryRoutes(limiter = RateLimiters.retrain())`.
3. `RateLimiterTest` rewritten on `TestClock`; the two negative-window tests in `InfraPluginsCoverageTest` moved to the clock; a plugin re-admission test.

## Security (§4a)
- **Exposure:** none new. No route, input, dependency or config. The auth, manual-sync and retrain limits are unchanged.
- **Abuse:**
  - *Before:* an impossible-but-unguarded null from `compute` would have counted the request on an untracked window, so it would always be allowed (fail open). *Now:* it throws, and the request fails with a 500 (fail closed).
  - The process-wide retrain limiter is gone, so one application's counters can't leak into another's (it mattered for test isolation; in production there is one application).
  - A flood of spoofed keys still can't grow memory without limit, and can't reset a client's count unless that client is among the oldest windows (tested).
- **Tests:** hostile and edge input in the unit tests: non-positive and oversized limits refused, exact window boundaries, a 2,000-key flood, a clock far from system time.
- **Playwright:** no screen, so no new spec.

## Risks / notes (found, not fixed: outside this step)
- **`Retry-After` rounds down.** With 0.5 s of a window left it says `0`, but a retry right away is still refused (the window ends strictly after its length). Fix: round up.
- **The key bound is really `max(maxKeys, 1001)`.** The sweep only runs above 1,000 keys, so a limiter with `maxKeys` below 1,000 can hold 1,001. Today every limiter uses the 10,000 default, so nothing is affected.
- **The sweep is O(n) on every request** once more than 1,000 keys are tracked (and a sort when over the bound). Fine for one owner; worth a cheaper sweep if limits are ever put on busy routes.
- **`StatementImportService.kt:51`** still has `seen.merge(key, 1, Int::plus)!!`, the other half of PROGRESS item 23.

## Resolution
`RateLimiter` reads time only from its injected clock, fails closed instead of the silent `?: Window(now)`, and validates its inputs. `RateLimiters` factories take a clock, and the retrain limiter is built per installation instead of process-wide. Tests run on `TestClock` with no sleeps, and cover window boundaries, Retry-After, the factories and the bounded key map. Files: `infrastructure/plugins/RateLimiting.kt`, `domain/financial/learning/LearnedCategoryRoutes.kt`, `RateLimiterTest.kt`, `InfraPluginsCoverageTest.kt`. Actual 1.5h vs ETA 1.5h.
