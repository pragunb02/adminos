## Parts
1. **Parsers** (transport-independent): `SmsParserRegistry` with per-bank `BankSmsParser` strategies, drop rules, `SmsMessage` → `IngestEvent`.
2. **Device token:** a scoped (`ingest:sms`), revocable token via the existing JWT + session system (approved by Pragun).
3. **Transport:** how SMS reach the API. Research in progress; Pragun to choose.
4. **Setup guide** for the chosen transport.

## Activity log
- 2026-10-16 — Claude: started part 1. Device token design approved; transport pending research.
- 2026-10-16 — Claude: **part 1 done** (parsers).
  - Types and parsers:
    - `SmsMessage` has a redacted `toString`.
    - `SenderId` parses TRAI headers (any operator prefix; rejects phone numbers).
    - One data-driven `BankSmsParser` per bank: HDFC, SBI, ICICI, Axis, Kotak, plus a generic fallback.
    - `SmsParserRegistry` applies the drop rules: OTP, promo `-P`, declined/failed, collect requests, upcoming-debit notices, balance-only alerts, personal numbers.
    - `SmsIntake` → `IngestEvent` with a sha256 `sourceRef`, so the same SMS under another operator prefix is a duplicate.
  - Tests: 15 parser, 2 sender id and 3 intake tests. Samples are **synthetic** approximations; they must be validated against real SMS locally. Unit 208/208.
  - Bug fixed during testing: the card-spend merchant pattern was too greedy (`HDFC Bank Card 5678 At AMAZON`, or a date for ICICI).
  - Transport research done (Tailscale serve / Mac Messages reader / Cloudflare Access …); Pragun to choose.
