## Description
Pragun: "add a review step (code and security reviewers) on every PR before merge. Do we have CI and GitHub checks and other good-practice things?"

**Findings (2026-10-18):** no CI ran on PRs (only GitGuardian); `main` had no branch protection; nothing recorded that a PR was reviewed.

## Acceptance criteria
- [x] `scripts/review-status.sh <pr> <kind> <state> <reviewed-sha> <findings>`: refuses if the head moved; posts the findings comment and sets `review/<kind>` on the reviewed SHA.
- [x] `scripts/merge-pr.sh` merges only when every check run succeeded and the newest `review/code` and `review/security` statuses are `success` and created by the owner, and pins the merge to that SHA (`--match-head-commit`); refuses more check runs than one page; validates arguments; is run from main's copy.
- [x] Tests with a fake `gh` that fails on unexpected calls and checks exit code, message and arguments: `scripts/tests/merge-pr.test.sh` (16) and `scripts/tests/review-status.test.sh` (9).
- [x] GitHub branch protection on `main` requires GitGuardian and both review statuses, admins included; secret scanning + push protection and Dependabot alerts on (Pragun approved, 2026-10-18).
- [x] ENGINEERING §4b, the Definition of Done, CLAUDE.md and the PR template describe the step; D-101.

## Design
1. **Commit statuses set by independent reviewer agents, enforced by the merge script** (chosen). A status is tied to one SHA, so a push after review can't merge; the script already gates every merge.
2. GitHub "required approving review": GitHub doesn't let the PR author approve their own PR, and every PR here is opened by the same account, so it would block everything or need a second account.
3. A PR comment checklist only: easy to skip; nothing enforces it.

## Security
The statuses are set with the owner's own token; the control is the process plus the merge script, not a cryptographic proof. Branch protection that requires `review/code`, `review/security` and the CI checks (with admins included) makes GitHub enforce it too: proposed to Pragun as a repo-settings change.

## Review findings on this PR (the step's first run)
- **Code review: blocked.** (1) a push during the merge wait would merge unreviewed (no `--match-head-commit`); (2) a verdict could land on a commit nobody reviewed; (3) `review-status.sh` had no tests; (4) refusal tests passed for any reason. Also: check runs not paginated, temp file left behind, arguments not validated. **All fixed.**
- **Security review: blocked.** The same (1) and (2), plus (3) an Actions workflow on a branch could post a forged `review/*` success, now refused unless created by the owner; (4) the merge script ran from the checked-out copy, so a PR could change its own gate, now always run from main's copy. Also: the docs overstated enforcement (now branch protection + honest limit), and comments must never quote sensitive data. **All fixed.**
