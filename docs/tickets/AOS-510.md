## Description
The push channel of D-51, using standard Web Push:
- the API stores one subscription per device and sends encrypted, VAPID-signed pushes;
- the web app has a service worker, a manifest for the Home Screen app, and **Settings → Notifications on this device**.

## Acceptance criteria
- [x] **Push channel:**
  - it is registered only when VAPID keys are set; otherwise Settings says push isn't set up and the API returns 503 `PUSH_001`;
  - a push goes to every device of the user, and one accepted device counts as delivered;
  - devices the push service reports gone (404/410) are removed;
  - 429, 5xx, timeouts and network errors are retried (D-51 backoff); other 4xx answers are permanent.
- [x] **Encryption and signing:**
  - RFC 8291 `aes128gcm` encryption reproduces the RFC's Appendix A example byte for byte, and a fresh message decrypts with the browser's keys;
  - VAPID (RFC 8292) is an ES256 JWT with the push service's origin as audience, a 12 h expiry and the configured contact; `k=` is the public key.
- [x] **Safety:**
  - the server only ever POSTs to Apple, Google, Mozilla or Microsoft push services, over https on the default port with no credentials in the URL (no SSRF through forged subscriptions);
  - endpoints are never logged or returned (they identify a device), and keys are never printed;
  - the tap URL is always a path inside the app (checked on the server and in the service worker).
- [x] **Devices:**
  - registering the same device again updates it;
  - a device belongs to whoever registered it last;
  - each user has at most 10 devices, and the oldest is dropped;
  - a user can turn off only their own device (404 `PUSH_002` otherwise).
- [x] **Test push:** "Send a test" pushes to all of the user's devices now, ignoring quiet hours, and reports the outcome.
- [x] **Configuration:** `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT` are validated at start-up (a half pair, a mismatched pair or a bad contact stops it); `./gradlew -q vapidKeys` generates a pair.
- [x] **Web:**
  - `public/sw.js` shows notifications and opens or focuses the app on tap; it caches nothing;
  - `manifest.webmanifest` plus icons (the Home Screen icon has no transparency, because iOS shows transparency as black);
  - the manifest, `sw.js` and the icons are reachable without a session.
- [x] **Settings explains each state:** checking, server not set up, iPhone tab ("Add to Home Screen"), browser can't, blocked, off ("Turn on notifications"), and on ("Send a test", "Turn off", device count). Failures show as alerts. If the server refuses the subscription, the browser subscription is undone.

## Design
- **Context:** iPhone Safari supports Web Push only for Home Screen apps (iOS 16.4+), which is the reason for the manifest and the explanation text. The only Java Web Push library (`nl.martijndwars:web-push` 5.1.2) depends on BouncyCastle 1.70, jose4j 0.7.9 and async-http-client 2.12, which are old versions with known vulnerabilities.
- **Options considered:**
  1. **Implement RFC 8291/8292 with JDK crypto plus Nimbus** (chosen). Nimbus is already used for JWTs. The code is small and the result is verified against the RFC test vector.
  2. Use the library: it is less code, but it brings the dependencies above.
  3. A hosted push service (OneSignal and others): a third party would hold user devices and message text, and it adds an account and an SDK.
- **Decision:** option 1 (D-52). **Patterns:** Strategy (the `PushSender` port, `WebPushSender` adapter), Registry (the `DeliveryChannel` from D-51), Value objects (`PushEndpoint` with the allowlist, `PushKeys`).
- **Extensibility:**
  - another push service is one host added to `PushEndpoint.PUSH_SERVICES`;
  - native APNs/FCM apps later would be another `PushSender`, or another channel.
- **Impact:**
  - API: `domain/notifications/push/*`, `infrastructure/push/*` (P256, WebPushEncryption, WebPushSender, VapidKeys), `/api/v1/push` routes, V19 `push_subscriptions`, `VapidConfig`, the Gradle `vapidKeys` task;
  - web: `sw.js`, manifest and icons, `lib/push.ts`, `PushDevice`, a guard exception for the static files, and a body on `api.delete`.

## Verification
- **API:** 1,146 unit and 101 integration tests, 0 disabled; 99.5% lines. Includes:
  - the RFC vector;
  - the HTTP sender against a local stand-in push service (headers, VAPID signature verified, body decrypted, every status class, timeout, unreachable);
  - routes and Postgres.
- **Web:**
  - 310 unit tests, 98.5% lines / 96% branches;
  - Playwright 226 passed and 7 deliberate skips; push runs on 3 browsers with the service worker really registered, and axe passes with push on.
- **Manual check for Pragun:**
  1. Generate keys (`./gradlew -q vapidKeys`) into `.env`.
  2. Open AdminOS in Safari, then Share → Add to Home Screen.
  3. Open it from the Home Screen, then go to Settings → Turn on notifications → Send a test.

## Risks / notes
- **Found by the tests and fixed:** the route guard would have redirected `manifest.webmanifest` (browsers fetch it without cookies) and `sw.js` updates to /login, which breaks Add to Home Screen.
- Changing the VAPID keys invalidates every subscription, so devices must turn push on again. This is noted in `.env.example` and in the key generator.
- The Settings page's older sections still use the legacy gray styling. This new section follows it so the page stays consistent.
