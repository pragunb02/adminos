## Description
- `JwtService` builds its HS256 key with `config.jwtSecret.toByteArray().copyOf(32)`, so **only the first 32 bytes of `JWT_SECRET` matter**.
- Two secrets that share their first 32 characters sign interchangeable tokens. A longer secret, e.g. `openssl rand -base64 48`, adds no strength.
- Found by AOS-311: a test token signed with the full secret was rejected.

## Fix
- Use the whole secret as the HMAC key (HS256 accepts keys of 32 bytes or longer; the length check stays).
- Add a regression test: two secrets with the same first 32 bytes must not verify each other's tokens.
- **Impact:** existing access tokens stop verifying once, so users sign in again (≤1h tokens; refresh tokens are server-side and unaffected).

## Acceptance criteria
- [x] The full `JWT_SECRET` is the key; regression test passes; device tokens and access tokens are both covered.

## Resolution
Done.
- **Fix:** `JwtService` uses the whole `JWT_SECRET` as the HMAC key; the ≥32-byte check stays.
- **Tests:**
  - `JwtServiceTest`: two secrets with the same first 32 bytes don't verify each other's access or device tokens (this fails on the old code); the signature equals HMAC-SHA256 over the full key.
  - End-to-end full stack: a forged token signed with a secret that shares the real one's first 32 bytes → 401 → login.
  - API unit 320/320, integration 51/51; full-stack end-to-end 5/5.
- **Impact:** existing access and device tokens signed with the truncated key stop verifying.
  - Users sign in once more.
  - The Mac SMS reader needs a new device token from Settings → Connected devices.
