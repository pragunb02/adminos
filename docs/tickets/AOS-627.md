## Description
`POST /push/subscriptions` upserted on the endpoint URL. When the endpoint was already registered by another user,
the row **moved** to the caller, along with the caller's keys. Now the registration is refused with 409 `PUSH_003`
and the existing row is left untouched (AUD-23, [AUDIT-2026-10](../security/AUDIT-2026-10.md)).

## Why
Anyone who learns a device's endpoint URL could take over that device's notifications and replace its encryption
keys. That would be a second account, or a stolen session (T3). AdminOS is single-user, so this is defence in depth
for the multi-user-ready model (D-5). Low, CVSS 2.2.

## Scope
- **In:** the repository contract (`save` returns a sealed result), both implementations, the service, the route, and the tests.
- **Out:** the web client (it already shows the API's error message); the device cap and unregister (unchanged).

## Acceptance criteria
- [x] Registering an endpoint owned by another user is refused: the service throws `PushEndpointTakenException`, and the route answers 409 `PUSH_003`. Tests: `a device registered to one user is refused to another and never moves (AOS-627)`, `registering a device another account already has is a 409 and changes nothing (AOS-627)`
- [x] The owner's row (id, keys, label) is unchanged, and the caller can't turn it off either (404). Tests: same two
- [x] Postgres refuses atomically: `ON CONFLICT (endpoint) DO UPDATE … WHERE user_id = <caller>`. Test: `NotificationRepositoriesIntegrationTest` › `push subscriptions keep one row per device, and another user can't take it over`
- [x] The same user re-registering still updates the row in place. Tests: `registering the same device again updates it instead of adding another`, and the integration test
- [x] Once the owner turns a device off, another user may register it. Test: `a device is free for another user once its owner turns it off`

## Design
- **Options considered:**
  1. Check-then-upsert in the service. Two requests could race between the check and the write.
  2. **An upsert whose update only applies to the caller's own row, then a re-read of the owner** (chosen). It is atomic in Postgres; the in-memory fake does the same under its lock.
- **Contract:** `PushSubscriptionRepository.save(subscription): PushSaveResult` (`Saved(subscription)` | `OwnedByAnotherUser`) replaces `upsert`. The rename makes every caller face the new outcome.
- **Liskov:** the in-memory fake now keeps `createdAt` on update, like Postgres does.
- **Impact:** API only. No schema change. The web shows the error message.

## Security (threat review, ENGINEERING §4a)
- **Exposes:** nothing new. It removes a way to move another user's row.
- **Abuse and what stops it:**
  - another user (or a stolen session) posting a known endpoint with their own keys: refused with 409, and the row is unchanged;
  - two concurrent registrations of one endpoint by two users: the conditional `DO UPDATE` lets only the owner's write through;
  - learning whether an endpoint exists: only someone who already holds the endpoint URL (a capability URL) can ask, and the answer names no account.
- **Tests that attack it:** unit, route and integration tests (above). The route was already authenticated and in the route inventory. There is no new screen, so there is no Playwright spec.

## Implementation plan
1. Sealed result and contract. 2. Exposed conditional upsert; in-memory fake. 3. Service exception; route maps it to 409. 4. Tests.
