## Description
Add an `e2e` job to `.github/workflows/ci.yml` that runs the whole Playwright suite on every PR and on `main`,
on every project (desktop-chrome, iphone-safari = WebKit, android-chrome, full-stack), and make it a required
check.

## Why
Since AOS-622 every gate runs in CI except Playwright (unit, integration, Go, parser, scans). The §4a security
gate's Playwright level (`e2e/security.spec.ts` and the rest) was run only by the integrator locally, so it was
both the merge bottleneck and easy to skip. Pragun asked that local test runs stop being the gate.

## Scope
- **In:** the `e2e` job; browser cache; a per-run JWT secret for the test API; the report and traces uploaded on
  failure; flaky tests annotated; `e2e` in `.github/required-checks.txt` and `docs/security/SUPPLY-CHAIN.md`.
- **Out:** turning `e2e` on in branch protection (the integrator, after merge); fixing flaky specs (reported as
  they show up).

## Acceptance criteria
- [x] Every PR runs `npx playwright test` with all four projects; the job is named `e2e`. → `ci.yml`
- [x] The servers are the ones `playwright.config.ts` starts: the in-memory API (`./gradlew run`, no database)
  and the production Next build, both on `127.0.0.1`; no published port, no service container.
- [x] Actions pinned by commit SHA, `permissions: contents: read`, `persist-credentials: false`, no repository
  secrets; the test API's JWT secret is random per run (`openssl rand -hex 32`), never printed.
- [x] Chromium and WebKit are cached by Playwright version; on a hit only the system libraries are installed.
- [x] On failure the HTML report and traces are uploaded (7 days); a pass on the CI retry shows as a flaky
  annotation (github reporter), not hidden.
- [x] `e2e` is listed in `.github/required-checks.txt`, so `scripts/merge-pr.sh` waits for it once this is on main.

## Design
- **Context:** `playwright.config.ts` already starts both servers (`webServer`), with `CI` giving `forbidOnly`,
  `retries: 1` and fresh servers. The suite's mocked projects answer `/api/*` in the browser; only full-stack
  (and the real-API half of `security.spec.ts`) talks to the in-memory API.
- **Options considered:** 1) one job running the config as it is (chosen: the same servers as locally, nothing to
  keep in step); 2) a matrix per project (4× the API and web builds for little gain); 3) the compose stack (needs
  secrets, Postgres and more time, and the suite is written against the in-memory API).
- **Secret:** the config reads `E2E_JWT_SECRET` from the environment, falling back to the fixed local value, so CI
  uses a random secret per run while local runs (and a reused local API) keep working. The tests forge tokens
  from the same constant, so both sides always agree.
- **Patterns:** fail closed (any failing spec fails the check); reuse of the existing config.
- **Impact:** CI only, plus two lines in `playwright.config.ts` (secret from the environment, github reporter in CI).

## Security (threat review, ENGINEERING §4a)
- **Exposes:** nothing new. The job runs PR code with a read-only token and no secrets (`pull_request`, never
  `pull_request_target`); both servers listen on the runner's loopback only.
- **Abuse and what stops it:** a malicious PR can't read secrets (there are none) or push (read-only token,
  credentials not persisted); a compromised action is limited by SHA pinning (Dependabot moves the pins).
  The uploaded report holds only synthetic fixture data (fixtures use `owner@example.com`) and expires in 7 days.
- **Checks:** no new dependency (Playwright is already in `package-lock.json`); no literal secret added; no bind
  widened.

## Verification
- `ci.yml` parses (YAML) and every `uses:` is a 40-character SHA with its version comment.
- The PR's own CI run is the end-to-end proof: the `e2e` job must pass on it.

## Risks / notes
- Known flake: `security.spec.ts` "sign-in starts at the API with a state and PKCE…" (full-stack) failed once
  locally and passed 5/5 on repeat. With one retry it would show as flaky; report it if it does.
- Run time is dominated by the Next production build and the API start; the job allows 60 minutes.
- Branch protection: add `e2e` to the required checks after this is on `main` (the integrator).
