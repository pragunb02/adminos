## Description
Import the CAMS + KFintech consolidated account statement (CAS, "Detailed": every folio and transaction) into the wealth ledger:
- the Python `pdf-parser` reads it with casparser (MIT, pinned) and returns decimal strings, with folio numbers in a separate block; the file and password are discarded (D-37), and the parser has **no outbound network**;
- the API encrypts the folio, records the rows in the append-only ledger as an undoable batch, and **reconciles** each holding: the ledger's units on the statement date must equal the statement's closing units, or the holding is blocked and listed for Review.

## Why
D-79 and WEALTH-RESEARCH §1.1: the CAS is the only source with full MF history and cost, which lots and XIRR need. Layouts are reverse-engineered and change, so reconciliation is mandatory.

## Scope
- **In:** `POST /v1/cas:parse` in `pdf-parser` (`app/cas.py`); `CasReader` port + `HttpCasReader`; `CasImportService`, `ReconciliationService`, `HoldingCheck` (V71); routes `POST /wealth/imports/cas`, `GET /wealth/imports`, `POST /wealth/imports/{id}/undo`, `GET /wealth/reconciliation`; compose: the parser on an internal-only network, read-only, no capabilities; synthetic golden PDF + JSON shared by both services.
- **Out:** NSDL/CDSL depository CAS (refused with `CAS_DEPOSITORY_UNSUPPORTED`; follow-up, see Risks); CAS "Summary" (refused: no history); the upload screen and Review list (AOS-820); Gmail auto-fetch (AOS-809); prices (AOS-810).

## Design
- **Context:** the statement flow (D-37) already sends files to `pdf-parser` in memory. casparser 1.x reads all four issuers with pypdfium2; it looks up ISIN/AMFI codes in a bundled SQLite database (local file).
- **Options considered:**
  1. **Reader:** (a) **casparser behind a port** (`read_cas`), with our own reconciliation in the API; (b) our own pdfplumber reader now. (a) is maintained and handles many templates; (b) would be weeks of reverse-engineering. Chosen (a); a second reader can replace it behind the port.
  2. **ISIN source:** casparser prefers a fuzzy name match from its database and drops a printed ISIN its database doesn't know (a fund launched after the database was built). (a) accept that; (b) **prefer the statement's printed ISIN** (hooking casparser's lookup, pinned version, guarded by a test), using the database only for the AMFI code and category. Chosen (b): the statement is the stronger evidence.
  3. **Where reconciliation lives:** (a) a stored status per import; (b) **store what each statement said (closing units, issue) and compute the status against the current ledger**. (b) stays right after an undo or after importing older history; chosen.
  4. **Granularity:** a whole folio, or **each folio × scheme**. Per scheme: one bad scheme doesn't hide the others in the same folio; Review groups by folio.
  5. **Bad rows:** (a) reject the whole file; (b) **keep the good rows, block the holding with the reason**. (b): reconciliation exposes it and a later file can fix it.
- **Decision:** proposed **D-129** below. **Patterns:** Port/Adapter (`CasReader`), Specification-like issue checks, shared contract fixture (golden JSON/PDF).
- **Extensibility:** NSDL/CDSL or a broker export is another reader returning the same JSON shape; a new row kind is one map entry (Python) and one `InvestmentTxnType`.
- **Impact:** new routes and one upload path (`RequestBodyLimits.UPLOAD_PATHS`); V71; compose network change (API joins `parser`).

## Security (D-100, docs/ENGINEERING.md §4a)
- **Exposes:** `POST /api/v1/wealth/imports/cas` (multipart, 20 MB), `GET /api/v1/wealth/imports`, `POST /api/v1/wealth/imports/{id}/undo`, `GET /api/v1/wealth/reconciliation`; parser endpoint `POST /v1/cas:parse` (internal network only, no published port); a new upload path; table `wealth_holding_checks`; new Python dependencies.
- **Abuse and what stops it:**
  - *Stranger / forged token (T1):* every route is in `authenticate("auth-jwt")`; route tests for signed-out and forged; the route inventory covers them automatically.
  - *CSRF:* `OriginCheck` (D-94) on the upload and undo; a request without same-origin proof is 403 (route test).
  - *Another user's import (IDOR):* lookups are `WHERE id AND user_id`; undo of someone else's batch is the same 404 as a missing one; lists show nothing of theirs (`IdorTest` rows and lists).
  - *Malicious PDF (T4):* parsed in its own container: non-root, read-only filesystem, no capabilities, `no-new-privileges`, **no network** (internal-only network; and verified to work with none at all), 20 MB cap on both sides (D-92 body cap first), 500-page cap before parsing, 90 s API timeout. casparser and pypdfium2 are pinned; pip-audit clean.
  - *Exfiltration by a compromised parser library (T5):* no route out of the parser network; the parse path opens no socket (test). Only `casparser-isin`'s CLI updater has network code, and it is never called.
  - *Hostile content in the statement:* folio numbers are validated (`[A-Z0-9/-]{1,40}`) before anything is written; one bad folio fails the whole import with nothing stored (test); scheme and AMC names are stripped to plain text in the parser and bounded; the API re-validates every number into exact types and refuses a reply that breaks the contract (`PARSER_CONTRACT`, tests); error codes from the parser are checked against a pattern before being echoed.
  - *Data minimisation:* the parser drops PAN, investor name, email, phone, address, nominees, advisor codes and descriptions; the folio is encrypted (D-128) and returned masked (••••4/56).
  - *Logs and audit:* both services log codes and counts only (tests); the audit row has counts and codes (`wealth.import`, `wealth.import_rejected`, `wealth.import_undo`).
- **Data at rest:** ledger rows (units, NAVs, amounts) and holding checks (scheme names, units, valuation) are not encrypted, justified in D-79; folio numbers are encrypted.
- **Dependencies:** casparser 1.4.1 (MIT), casparser-isin 2026.6.9 (MIT), pypdfium2 5.14.0 (Apache-2.0/BSD-3), pinned; latest stable on 2026-10-18; pip-audit: none known.

## Proposed decision D-129 (for the integrator)
### D-129 — CAS import: casparser behind a port, the printed ISIN wins, reconciliation computed against the ledger, a parser with no network
2026-10-18 · Proposed · Type: Architecture · Tasks: AOS-805 · Builds on D-37, D-79, D-97, D-128
- **Reader:** casparser (MIT, pinned with pypdfium2 and its ISIN database) in `pdf-parser`, behind `read_cas`; CAMS/KFintech "Detailed" only for now (Summary has no history; NSDL/CDSL later as a cross-check). The printed ISIN beats casparser's fuzzy name lookup; the database adds only the AMFI code and SEBI category.
- **Minimum data:** the parser returns schemes, rows (kind, signed units, gross amount, NAV, running balance) and valuations as decimal strings, and folio numbers in a separate block; it drops PAN, the investor's name, email, phone and address, nominees, advisor codes and descriptions.
- **Reconciliation:** each import stores, per folio × scheme, the statement's closing units, valuation and any reading issue. The status is computed against the current ledger on the statement date: equal → reconciled; otherwise blocked with a reason (units mismatch, history missing, unrecognised or contradictory row, running-balance break, unidentified scheme). The latest statement per holding counts; undo and older imports re-judge it. Blocked holdings are shown in Review and kept out of holdings and returns.
- **Isolation:** the parser runs read-only, non-root, without capabilities, on an internal-only network shared only with the API; the parse path opens no socket.
- **Rejected:** our own CAS reader now (effort, layouts); trusting casparser's database over the printed ISIN; a stored reconciliation status (wrong after undo); rejecting a whole file for one bad row; a whole-folio block.
