## Description
Which Gmail messages count as bank mail was decided from the unauthenticated `From` and `Subject` headers, and a
subject phrase alone admitted a message (AUD-11, [AUDIT-2026-10](../security/AUDIT-2026-10.md)). Qualify mail by
sender only, and require Gmail's own `Authentication-Results` to authenticate that sender.

## Why
A stranger's email that merely looks like a bank alert could add entries to the ledger, change totals and dues,
and put attacker-chosen text in alerts (T4 in the threat model). Medium, CVSS 5.3.

## Scope
- **In:** the Go Gmail worker: the sender list, the full-sync search, the incremental metadata check, a local
  re-check of every fetched message, a reject counter.
- **Out:** the API (it never reads mail: the worker writes `ingest_events` itself); SMS and WhatsApp (their
  sender trust is TRAI headers and display names, D-66); ARC (Gmail is the receiving MX for the owner's mailbox).

## Acceptance criteria
- [x] A subject phrase never admits a message (search query and local check). — `TestSearchQueryIsBoundedAndFilteredBySenderOnly`, `TestASubjectAloneNeverAdmitsAMessage`, `TestQualifyNeverAdmitsByDisplayNameSubjectOrMalformedFrom`
- [x] Mail from a listed sender is read only when Gmail's topmost `Authentication-Results` (authserv-id `mx.google.com`) shows `dmarc=pass` for the From domain or `dkim=pass` for a domain aligned with the sender's organisation. — `TestQualifyAdmitsAuthenticatedBankMail`, `TestQualifyRejectsSpoofedBankSenders`
- [x] A spoofed bank email is never fetched in full on an incremental sync, and never parsed on a full sync. — `TestIncrementalSyncNeverFetchesSpoofedBankMail`, `TestFullSyncQualifiesEverySearchResultLocally`
- [x] Rejects are counted (`unauthenticated` on the result, and in the sync log line). — same tests
- [x] Malformed or multiple From headers, display-name tricks and look-alike domains are refused. — `TestSenderAddressAcceptsOnlyOneWellFormedAddress`, `TestSenderOrganisation`

## Design
- **Context:** `filters.go` had sender domains, addresses and subject phrases; `IsFinancial(from, subject)`
  admitted on any match; the full sync trusted Gmail's search `from:(…) OR subject:(…)` and never checked locally.
- **Options considered:**
  1. Keep the subject list but only as a narrowing filter (sender AND subject). Drops genuine alerts whose
     subject isn't listed, and adds nothing to authenticity.
  2. **Sender only + Gmail's authentication verdict** (chosen).
  3. Verify DKIM ourselves from the raw message (`format=raw`). Reads every candidate's full body and needs DNS
     from the worker; Gmail has already done it at delivery.
- **Decision:** `gmail.Qualify(headers) → NotBankMail | Unauthenticated | BankMail`:
  - exactly one `From`, exactly one address (strict parse, no lenient fallback), whose domain is a listed
    sender; the listed entry is the sender's **organisation** (a `bank.in` sender's organisation is
    `<bank>.bank.in`, so siblings under the registry never align);
  - only the **topmost** `Authentication-Results` is read and its authserv-id must be `mx.google.com`: Gmail
    prepends its own, so any header the sender wrote is below it;
  - comments are stripped (nested, escaped) before clauses are split, so text an attacker controls inside a
    comment (the envelope sender quoted in the SPF comment) can't add a clause; a property given twice is void;
  - `dmarc=pass header.from=<From domain>` or `dkim=pass` with `header.d` (else `header.i`) inside the
    organisation qualifies; SPF alone never does (it authenticates the envelope, not the From).
  - The incremental sync reads only `From` and `Authentication-Results` metadata (no longer the subject), and
    every full fetch is qualified again, so the full sync's search is a pre-filter only.
- **Patterns:** Specification (one verdict function), data-driven sender list.
- **Extensibility:** a new bank is one line in `FinancialDomains` (or nothing, under `bank.in`).
- **Impact:** worker only; `GmailResult` gains `unauthenticated`. No schema, contract or API change.

## Security (threat review, ENGINEERING §4a)
- **Exposes:** nothing new: no route, input, job, dependency or stored field. It narrows what the worker reads.
- **Abuse and what stops it:**
  - spoofed `From: alerts@<bank>` from any server → DMARC fails at Gmail; no DKIM for the bank domain → `Unauthenticated`, never fetched in full;
  - a forged `Authentication-Results: mx.google.com; dmarc=pass …` inside the message → below Gmail's, never read;
  - bank name or address in the display name, `From` with two addresses, two `From` headers, unparseable `From` → `NotBankMail`;
  - look-alike domains (`hdfcbank.net.evil…`, `nothdfcbank.net`), another bank under `bank.in` signing → not aligned;
  - a clause smuggled through the SPF comment's envelope address, unbalanced comments, duplicated properties → refused;
  - a stranger with a bank-alert subject → never read (the subject no longer admits);
  - a genuine bank account compromised and sending fake alerts → out of scope (it would pass DMARC; the pipeline's
    dedup and review still apply).
- **Fail closed:** missing, empty, non-Gmail or unparseable headers all reject.
- **Privacy:** the subject is no longer requested on the metadata pass; nothing about rejected mail is logged
  except a count (D-33).
- **Tests that attack it:** unit (spoof, forged header below Gmail's, comment smuggling, duplicates, look-alikes,
  malformed From, subject-only) and handler-level against a fake Gmail (incremental and full sync). No route or
  screen, so no route-inventory or Playwright specs.

## Implementation plan
1. `filters.go`: drop subjects, sender organisation, strict From parse. 2. `authn.go`: `Qualify` + RFC 8601
parsing. 3. Sync: metadata headers, re-check on full fetch, counter. 4. Tests.

## Risks / notes
- A genuine bank whose mail neither passes DMARC nor carries an aligned DKIM signature would now be skipped
  (counted as `unauthenticated`). Every listed Indian bank publishes DMARC; if a biller doesn't, its mail shows up
  in the count and the list can be reviewed.
- Mail that reached the mailbox other than through Gmail's MX (POP fetch, import) has no Gmail
  `Authentication-Results` and is rejected. Fine for this mailbox.
