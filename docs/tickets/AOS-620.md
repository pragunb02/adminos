## Description
D-91 layer 3 (session): the owner hears about every new or refused sign-in, can see and cut off every session, a
stolen refresh cookie is detected on reuse, and an access token dies with its session. **AOS-121 was not done, so it
is done here** (rotation + reuse detection). Closes audit findings AUD-04, AUD-05, AUD-10.

## Acceptance criteria
- [x] **Alerts (push + email + in-app, type `security`, never held by quiet hours, can't be switched off):**
  - a new sign-in from a device/address not seen in the user's last 50 sessions;
  - a refused sign-in (a stranger's or unverified Google account, or an impostor of the pinned account), batched: at most one alert per 15 min with the count since;
  - a reused (rotated-out) refresh token: the session is revoked and the owner told.
- [x] **No attacker-controlled content in alerts:** device names come from a fixed vocabulary ("Chrome on Mac"), never the raw user agent; a refused account is masked to `x•••@y•••.tld` with letters/digits only; no IP (spoofable, AUD-03). Coarse location: not available offline, so omitted (see notes).
- [x] **Settings → Security** (`/settings/security`): sessions with device, last active, sign-in time and "This device"; sign out one; sign out everywhere else; sign out everywhere (confirmed).
- [x] **Rotation with reuse detection (AOS-121):** every refresh issues a new refresh token; the old one is remembered; presenting it again after 30 s revokes the session (`AUTH_009`) and alerts; within 30 s (two tabs) it gets an access token only.
- [x] **Access tokens die with their session (AUD-04):** tokens carry `sid`; every request checks the session is live and the user's; with a database a token without `sid` is refused.
- [x] Revoking this device's own session clears its cookies; sign out everywhere clears them and ends every token at once.

## Design
- **Rotation options:** 1) **rotate on every refresh, keep a history of rotated hashes, revoke on reuse, 30 s grace for concurrent tabs** (chosen; RFC 9700 §4.14); 2) keep only the previous hash on the session (misses older replays); 3) refresh-token families as separate rows (more schema for one user).
  The rotation is one conditional UPDATE + history insert in one transaction, so concurrent refreshes have one winner; the loser gets an access token only.
- **Ending access tokens options:** 1) **`sid` claim + per-request session lookup** (chosen: single user, one indexed lookup per call); 2) shorter access TTL only (still a window); 3) a revocation list (state anyway, with less meaning).
  In-memory dev mode accepts tokens without `sid` because tests and the full-stack e2e mint them directly; with a database nothing without a live session gets in.
- **Alert delivery options:** 1) **a `SecurityNotifier` port in identity, implemented with the existing notification service** (chosen: push/email/in-app with retries, D-51; identity doesn't reach into notifications); 2) a direct email call from the auth route (no push, no retry, layer breach).
- **What "new" means:** device label + address pair not seen in the last 50 sessions. Behind the default (no trusted edge) every address is the proxy's, so it is effectively per device.

## Security (D-100 §4a)
- **Exposes:** `POST /api/v1/auth/sessions/revoke-all` (session-only, CSRF-checked); a `security` notification type; table `session_rotated_tokens` (hashes only). Migration V33 .
- **Abuse and what stops it:** stolen refresh cookie → rotation + reuse detection + alert; stolen access token → dies on logout/revoke; alert flooding by a stranger → batched; alert content injection (UA, email) → fixed vocabulary and masking; token without session in production → refused.
- **Tests:** unit (rotation, race, grace, reuse, revoked, masking, device labels, batching, failure-safe delivery), route (sessions list, revoke one/all/keep current, cookies cleared, sid enforced, DB-mode sessionless token refused), integration (Postgres rotation race, history, revoke-all, `security` enum), web (component + page), Playwright (security page, untrusted device text, sign out everywhere → login).

## Risks / notes
- **Owner action:** none required. Alerts reach push/email only if those channels are configured (VAPID, SMTP); in-app always.
- Existing sessions from before this change carry no `sid`: with a database they must sign in again once (nothing is deployed yet).
- Coarse location: an offline GeoIP database would add a licence and a dependency for little value on a private network; left out. Revisit if the app is ever reachable from the internet.
- Two tabs refreshing more than 30 s apart with the same old cookie can't happen in one browser (cookies are shared); a reuse that late really is a copy.
