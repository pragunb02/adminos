## Description
Rename `infra/migrations/00N_*.sql` → `V{N}__*.sql`, move them to `services/api/src/main/resources/db/migration`, remove the docker-compose initdb mount, and update the integration-test path and README.

## Why
Flyway ignores the current names, so migrations never run; two runners would conflict.

## Acceptance criteria
- [x] Fresh DB: API start applies V1…V8; a second start applies 0 (`flyway_schema_history` shows 8 successful rows)
- [x] No initdb mount in compose; `infra/` removed

## Implementation plan
1. git mv files
2. Update DatabaseFactory locations
3. Update the test path, compose and README

## Verification
- AOS-104

## Activity log
- 2026-10-16 — Claude: ticket created (AOS-004).

## Resolution
- **Migrations:** `infra/migrations/00N_*.sql` → `services/api/src/main/resources/db/migration/V{N}__*.sql` (`git mv`, history kept). Flyway is the only runner.
- **`DatabaseFactory`:**
  - `isConfigured()` is the single source for "database configured?", used by both DI and startup (they disagreed before).
  - `migrate()` fails fast and returns the count applied.
  - `baselineOnMigrate` removed; `filesystem:` location removed.
- **Startup:**
  - No `DATABASE_URL` → explicit in-memory dev-mode warning.
  - DB/migration error → the app **exits** (verified: exit 1 with "Connection refused"). It used to swallow the error and run.
- **Test:** runs real Flyway; new test `re-running migrations is a no-op`.
- **Verification:**
  - Unit tests green; integration **9/9**.
  - Real `./gradlew run` against compose Postgres 18: 8 applied → restart 0 applied → `/health` OK.
- Actual 0.75h vs ETA 1h.
- **Follow-up (AOS-110):** compose has the workers start once Postgres is healthy, but the schema now appears only after the API has migrated. Add an API healthcheck and make the workers depend on it.
