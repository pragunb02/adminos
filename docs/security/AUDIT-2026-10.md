# Red-team audit, October 2026

_AOS-615 · Auditor: Claude (security engineer / red team) · 2026-10-17 · Baseline: `main` at 551ca24 · Threat model: [THREAT-MODEL.md](THREAT-MODEL.md)_

**Scope:** the Kotlin API (every route, plugin, auth path, webhook, device tokens, uploads), the Next.js web
(proxy, route guard, config, every page that renders untrusted text, the service worker), the statement parser,
the Go workers and the Mac SMS reader (inbound surfaces), `docker-compose.yml` and every Dockerfile, and the
dependency trees of all five components.

**Method:** OWASP ASVS 5.0 Level 2 (chapters V1–V16) and OWASP WSTG test cases, against the attackers T1–T6 of
the threat model. Code read route by route; attacks run against a local in-memory API and a production Next build
on loopback (never against anything deployed: nothing is). Each finding has a CVSS 3.1-style base score, an
environmental note, a proof (a failing-before / passing-after test where possible) and a fix.

**Disclosure rule (public repo):** findings fixed in their own PR are described fully. Open findings are described
only as far as needed to fix them; nothing is deployed yet, and the network layer (AOS-616) is what keeps strangers out.

### AUD-01 — Bodies were read before any size check (High, fixed)
- **Attack (T1):** `POST /api/v1/auth/google` needs no session. A request declaring and sending a 100 MB JSON body
  was read and decoded in full (measured: answered 400 after reading all of it). Concurrent requests multiply the
  heap used; the auth rate limit (10/min/IP) didn't help because the IP is spoofable (AUD-03). Authenticated routes
  were protected only because authentication happens to run before the handler reads the body.
- **Fix:** `RequestBodyLimit` (`infrastructure/plugins/RequestBodyLimit.kt`), installed before routing:
  `Content-Length` is required for a body (chunked without a length → 411); over the path's limit → 413 straight
  from the headers. Default 1 MiB; only the three upload routes (exact paths, POST) get 21 MiB, and their handlers
  keep their exact 20 MB checks. Verified that the Next proxy keeps `Content-Length`, so the browser path is unaffected.
- **Proof:** `RequestBodyLimitTest`: against the real Netty server, a sign-in request *declaring* 100 MB and sending
  nothing gets `413` immediately (the old code would have waited for the body); a chunked body gets `411`; an
  over-limit JSON body never reaches its route; upload paths get the larger limit only on exact POST paths.

### AUD-02 — Known-vulnerable Jackson; unused JWT library (Medium, fixed)
- **What:** OSV listed GHSA-7hhh-6rmp-j9qf, GHSA-p6pp-m3f8-5c89, GHSA-cxp5-3px4-pw24, GHSA-q4xh-88c3-wmh7,
  GHSA-wv8q-qhhj-9h54 (High) and GHSA-5gvw-p9qm-jgwh, GHSA-5jmj-h7xm-6q6v, GHSA-gx83-3vf8-gh7j,
  GHSA-vvgp-rfg2-7rr6, GHSA-wjgm-6hv5-3cvf (Moderate) for jackson-core / jackson-databind 2.22.0, fixed in 2.22.3.
- **Environmental:** Jackson parses only TLS responses from Google and Anthropic here, never request bodies (those
  use kotlinx.serialization), so reachability is low. Policy is still to apply security fixes immediately (ENGINEERING §7).
- **Fix:** `jackson-bom` 2.22.3 as a platform in the build (lifts every transitive Jackson module), and removed
  `ktor-server-auth-jwt`, which nothing used and which pulled in a second JWT library (`com.auth0:java-jwt`).
- **Proof:** OSV re-scan of the resolved runtime classpath: 223 artifacts, 0 vulnerable. `DependencyFloorTest`
  fails if Jackson drops below 2.22.3 or the second JWT library comes back.

### AUD-03 — Client IP is client-controlled without an edge proxy (Medium)
- **Verified:** a production Next build forwards a client-sent `X-Forwarded-For` to the API unchanged (it only adds
  one when none is present), and middleware can't tell the two apart. The API trusts the last hop (D-32), so
  rotating the header bypassed the per-IP auth limit in a local test, and the IP recorded on sessions and audit rows
  is the attacker's choice. D-32 anticipated this ("a deployment must run an edge proxy that sets XFF").
- **Fixed (AOS-618):** the API distrusts forwarded headers by default and uses the TCP peer; `TRUST_FORWARDED_FOR=true`
  is for a deployment whose edge appends the real peer (AOS-616). Security decisions never depend on the IP alone
  (the lockout only delays; sign-in alerts label it as reported, AOS-620). Tests: `HardeningTest` (XFF ignored by
  default, last hop used when trusted, strict parsing of the setting).

### AUD-11 — Bank mail isn't authenticated (Medium, AOS-624)
- **Risk (T4):** which messages count as bank mail is decided from the `From` and `Subject` headers, and a subject
  phrase alone qualifies a message. Neither is authenticated, so mail that merely *looks* like a bank alert can
  reach the parsers. Impact is integrity (fake entries, misleading totals and dues) and attacker-chosen text in alerts.
- **Fix (AOS-624):** qualify by sender only (known bank domains/addresses), and require Gmail's own
  `Authentication-Results` to show DMARC pass (or aligned DKIM/SPF pass) for that domain; a subject phrase may only
  narrow, never admit. Unit tests with spoofed-From and subject-only messages; a metric of rejects.

### AUD-12 — Redis without authentication (Medium, AOS-616 / AOS-622)
- Any process on the host, or any container on the compose network, can read and enqueue worker jobs. Handed to
  the infra tasks: Redis `requirepass`/ACL with the URL from `.env`, and no host publish for Redis or Postgres
  unless a developer opts in.
